CmdQ user manual

This manual covers the current version of CmdQ. Names in bold match the English UI. New to CmdQ? Install it first with Get started on the home page.

Queued tasks run Claude Code with --dangerously-skip-permissions. Claude Code will read, write, and delete files and run commands in the target folder without asking you first. Review what you queue, keep your work under version control, and use this app only on folders you are willing to let it change. You are responsible for the results of the tasks you run.

The window

Header

  • 5-hour window and Weekly limit bars show how much of each limit you've used. The ring shows the 5-hour figure.
  • Next reset counts down to the next 5-hour reset. Weekly reset does the same for the weekly limit.
  • When the weekly limit is used up, the label changes to Weekly limit · resumes and the queue waits for the weekly reset.
  • Unreadable means the last usage check failed. N/A means your plan doesn't report that value.
  • On the right: N terminals (only while background terminals exist), 🔍 Search questions (⌘K, left of ☆; see Progress and history), ☆ Bookmarks, the light/dark toggle, and ⚙ Settings.
  • When questions are waiting for your answer, a ? Decide N badge appears left of 🔍. Click it or press ⇧⌘C to open the Decision inbox.

Project tabs

Each tab is one project folder. Click + Folder (⌘O) to open one. A tab shows only the items for its path, and the add bar uses that path. Switching tabs resets the add bar to the Path target and the To Do queue.

Closing a tab (⌘W or the tab's ×) deletes nothing. Auto queue items for that path keep running. Drag tabs to reorder them.

Turn on Show all (⇧⌘A) to see items from every open tab, grouped by path. Dragging cards is locked while it's on.

Queues and item numbers

Below the add bar are two lists: Auto queue and To Do. In the auto queue, the circle on the left of a card is its place in line. It turns into a pulsing light while the item runs and a ✓ when it's done. The #12 chip is the item's ID. It never changes, and notifications use it to name the item.

Menu bar icon

CmdQ keeps running in the menu bar after you close the window, and the auto queue keeps going. Choose Quit (⌘Q) in the menu to stop it.

Click the icon for a menu showing your plan, both usage figures, reset countdowns and an auto queue summary. Below that: Refresh usage, Open window, Settings…, Open log folder, About, Check for Updates…, Report a bug, Request a feature, ❤️ Support CmdQ — Star on GitHub, Sponsor… and Quit. Report a bug opens a prefilled GitHub issue in your browser with the app version, macOS version and CPU type. Nothing is sent until you submit it.

CmdQ checks for a new version about 20 seconds after launch and every 6 hours after that. When one is available it asks first, and only downloads, installs and restarts when you choose Install and Restart. If auto queue tasks are running or interactive terminals are open, the prompt says they will be stopped by the restart. A version you put off with Later isn't offered again until the app restarts; in the meantime you can install it from Check for Updates…, which also tells you when you're already up to date.

  1. Open a project tab with + Folder.
  2. Type the prompt or command you'd give claude, for example /code-review or Fix the failing login test.
  3. Press a submit key, or click Add to use the queue picked in the add bar.

Skill autocomplete

Start a word with / and a list of your skills opens, labeled User, Project or Plugin. ↑ ↓ move the highlight, Tab inserts the skill, Esc closes the list. Enter does not pick a skill. It submits the text exactly as typed.

Images and paths

  • Paste an image and it shows up as [IMAGE]. CmdQ saves the image and hands its path to claude when the task runs. Backspace right after the marker deletes it.
  • Type @ to browse files and folders under the tab's path (or the session's folder for a session target). Tab or Enter inserts the path.
  • Type # to insert attachment markers. See Attachments.

Session target

  • Click Session, then pick from the session list for the tab's path. Each row shows how much of the context window that session has used. Sessions you started with Interactive carry an Interactive badge.
  • 🕐 History lists the questions asked in the selected session.
  • ▶ Terminal opens the selected session in an interactive terminal (Interactive terminal).

Interactive target

The text in the command box becomes your first message. An empty box opens a blank session. It won't open while the add bar holds pending attachments or attachment markers, because markers aren't expanded in an interactive session.

Changing a card's target

The small button next to a card's path or session chip switches the target: Switch to a session on a path card, Switch to a path on a session card. It isn't shown on running or finished items, on chain parents or on chain children.

Auto queue and To Do

Auto queue

Runs from the top on its own. Items paused at a limit go before newly queued ones once the limit resets.

To Do

A holding list. Nothing here runs until you promote it. Each card shows how long ago it was captured and warns when the context may be stale.

How many run at once

  • Within one path, the auto queue runs one item at a time, top to bottom.
  • Different paths run side by side. Auto-queue concurrent runs (default 3) caps how many paths go at once. Runs you start by hand don't count.
  • Concurrent runs per path (default 2) caps automatic plus manual runs in one path. At most one of them is automatic. Set it to 1 if your tasks edit files, because two runs touching the same file overwrite each other, or run the tasks that may overlap as isolated runs.
  • Session targets also wait while their session is busy.

Moving items

  • ▶ Promote to the auto queue on a To Do card moves it to the end of the auto queue. It starts when its turn comes.
  • Move to To Do on a waiting or failed auto queue card moves it back.
  • Drag a Queued or Waiting for reset card up or down to change the order. Running and finished cards stay put.
  • When two or more auto queue cards target the same session, they are grouped under one card, placed where the first of them to run sits; finished cards ahead of it move into the group. Replies you add with Send to queue in the decision inbox join the path card that first ran that session, starting with the first reply. If the group has a path card, that card is always in front, so you can see which task the replies came from. Otherwise the front card is the running one, otherwise the queued one that runs next, otherwise the most recent. Click N more in session to show the rest below it; while the group is collapsed, the button also counts the running and queued cards inside (for example 1 more in session · 1 queued). Those cards can't be dragged. Dragging the front card moves the whole group and keeps its run order, even when the front card is a finished path card, as long as the group still has a queued card; dragging any other card moves only that card. Either way, the cards you didn't drag keep their run order, and a card dropped right below a group doesn't become its child even if you drag it to the right.

Chains

A chain is a parent task with follow-up tasks nested under it. Each child waits for the step before it, then runs in the parent's claude session, so it sees what the parent did.

#21 Refactor the auth module to use the new token store ~/work/api ↳ #22 Run the test suite and fix anything that broke ↳ #23 Draft a commit message for these changes

Making a chain

  1. Add the parent and the follow-up tasks to the same path, in the order you want them to run.
  2. Drag a follow-up card a little to the right while moving it (about 32 px). The drop slot indents.
  3. Release. The card becomes a child of the card above it. If the card above is itself a child, the new card joins the same parent as its next sibling.

Rules for nesting:

  • Both cards must use the Path target. Session tasks can't be nested; tasks for one session already run in order.
  • Chains go one level deep. A card that already has children can't become a child.
  • Only Queued or Waiting for reset cards can be dragged. This works in both the auto queue and To Do.
  • Dragging is locked while Show all is on. Pick a single tab first.
  • Use ▾ / ▸ on the parent to expand or collapse its children.

Recovering from a failed parent

  1. Click Run interactively on the failed parent. Its session opens in an interactive terminal with the earlier conversation.
  2. Talk claude through the fix, or send one message such as continue.
  3. Your first message marks the parent Done. The child resumes the parent's session, so it waits while a terminal still holds that session. Click Terminate on that terminal, and the first child starts on the next queue check.

Editing a chain

  • Detach from the chain (run standalone) on a child turns it into a normal item, placed after the rest of the chain. It stops waiting for the parent.
  • Stop (move back to queued) on any running item in a chain moves the whole chain to To Do. Finished steps stay Done. Promote the parent later and the chain picks up at the first unfinished step.
  • Move to To Do on a parent, or on a failed child, also moves the whole chain.
  • Delete on a parent deletes its children too, and stops any of them that are running.
  • Children have no 📎 button. They share the session's attachments, so add them from the parent card's 📎.
  • Children have no ▶, ⌘ or ☆ buttons of their own, except that a failed child gets Re-run and Move to To Do.

Example: build, then explain the failure

Run the production build and fix type errors ~/work/web ↳ If anything still fails, summarize the remaining errors and likely causes

The child reads the build output already in the session, so you don't need to paste logs into the second prompt.

Example: refactor, test, write the commit message

Refactor src/payments to remove the legacy client ~/work/api ↳ /test ↳ Draft a commit message for these changes. Don't commit

If /test fails, the commit message step waits. Fix the tests (or re-run the child) and the last step follows.

Usage limits and auto-resume

Claude Code has a 5-hour usage window and a weekly limit. Both are account-wide. When one runs out, CmdQ pauses all work and resumes it after the reset.

When a limit is reached

  • CmdQ stops every running queue item, not only the one that hit the limit. Each goes to Waiting for reset.
  • Interactive terminals are closed (reclaimed). A terminal opened from a card puts its item in Waiting for reset.
  • A terminal with no card (opened with Interactive, ▶ Terminal or a bookmark) gets a row in the background terminal list: Waiting for reset · resumes HH:MM. Click the row to read the past conversation. Cancel resume keeps it from reopening.
  • You get a Terminal reclaimed notification for each closed terminal, and the menu bar icon gets a yellow dot.
  • The auto queue banner shows how long until queued items start again.

After the reset

  • Paused items run first, in the same claude session, with this prompt instead of the original command: Continue the work you were doing. Pick up from where it stopped and do not redo what is already finished.
  • An item that hit the limit before it had a session reruns its original command.
  • Card-less terminals reopen in the background with the same prompt. No window pops up. A toast says how many were resumed. Open them from N terminals.
  • After a weekly limit, the queue waits for the weekly reset, not the 5-hour one.

Statusline connection

On first launch CmdQ asks once whether to connect Claude Code usage. Connect points statusLine in ~/.claude/settings.json to a CmdQ wrapper, so usage updates faster and more accurately. Your existing statusline display stays as it is. Later keeps the periodic /usage checks only. Either way, CmdQ doesn't ask again for that Claude config folder, and Settings has no switch for it.

Recurring schedule

One rule creates a queue item at the times you set. The items it creates run in the same queue, in the same way, as items you add by hand.

Overview

  • The Queue and Schedule switch in the header changes the screen. The Schedule screen has two views, List and Calendar.
  • It is a free feature, and there is no limit on the number of rules.
  • Times follow this Mac's local time zone.
  • A rule creates its runs while CmdQ is running. Runs that passed while it was off are handled as you choose under Conditions.

Creating a rule

Click New rule to open the New schedule rule editor. The name, command, and path are required.

  • Name and Command. Add step turns the command into a chain. Each step continues in the same session after the previous one finishes.
  • Path. Choose path picks the folder.
  • Add to. Auto queue runs each created item from the queue right away. To Do only creates the item, and you run it yourself.
  • Alert when done 🔔. Applies to cards this rule creates (recurring runs, Run now, and later chain steps). You can still change each card with its own 🔔, and changing the rule later does not change cards it already made. If unset, it shows Follows default (on now) or Follows default (off now) and follows 🔔 on new cards. Click it to set On or Off, and Use default to go back.
  • Repeat and Conditions are described below.
  • The editor's Next 5 runs previews the next five times. They are theoretical times with conditions not applied.

Conditions

  • Skip a run when weekly usage is over the limit. The Threshold (%) is 1 to 100, and the default is off. If usage is unknown, the run is not skipped. It runs, and the run history notes Usage unknown.
  • If the previous run is still in the queue, choose Skip this run (default) or Add another. In the queue means Queued, Running, or Waiting for reset, and To Do items count too.
  • For runs missed while the app was off, choose Run once on launch (default) or Skip. Running once creates only the most recent missed run since the last check. Right after you create, re-enable, or edit a rule, past runs are not backfilled. Even while the app is running, runs are created once per Queue check interval, so a run counts as missed only after the longer of 2 minutes or twice that interval has passed.
  • A rule turns off automatically after 3 consecutive failed runs, and this always applies. The card gets a Turned off after failures badge and a toast says the rule was turned off after 3 consecutive failures. Only runs that end in an error count. A run you stop, a run waiting for reset, and a skipped run neither count nor break the streak, and a success resets it to 0. Turning the rule back on clears the badge and the count. Unless Notification style is set to Off in Settings, you also get a system notification. This one doesn't depend on the card's 🔔.
  • A run handed to an interactive terminal, or started interactively from its card and finished, is recorded as Succeeded and resets the failure count to 0.

Completion criteria and exceptions

Both fields in the editor are optional. What you write is appended to the end of the command under a fixed heading. In a chain, it goes on the last step.

  • Completion criteria (optional): state how to judge whether the result is useful. It is appended under the heading [완료 기준].
  • When data or destination is missing (optional): appended under the heading [예외 처리]. On a new rule this field is empty, and "If the requested data or destination is missing, do not send it elsewhere or change the scope; state what was missing and stop." shows only as grey hint text (an example). If you leave it empty and save, nothing is appended. When you edit an existing rule, the saved value is shown as it is.
  • The headings are the same in every app language.
  • CmdQ does not judge whether a result met the criteria. You check it yourself with View the response on the run item.

Sessions and attachments

  • By default, each run starts a new session.
  • Turn on Continue the last run's session to continue the previous run's session. Context keeps accumulating, so a long-running rule can get heavy. If there is no previous session, the run starts a new one. A chain continues the session of its last step. A continuing rule copies attachments only on its first run.
  • The rule's 📎 attachments are copied to each run item. Editing the rule's attachments does not change items that were already created.
  • Links in a rule's attachments have no Save text. Use it on the copy of the link in a run item instead.

Isolated runs

When two tasks edit files in the same path at the same time, one set of changes can overwrite the other. An isolated run puts such an item in its own git worktree next to the repository, and when it ends you decide what happens to the result. Nothing is merged automatically. Items that are not isolated run exactly as before.

Turning it on

  • Turn on the Isolated run toggle on the row below the add bar before you add the item. It is off by default. The row appears only when the target is Path and that folder is a git repository. For session or interactive targets, or a folder that isn't a git repository, the row doesn't appear. With a missing git, a git older than 2.5, or a bare repository, the toggle stays off and the reason appears next to it.
  • When the same path already has a running or queued task, a Run isolated? badge appears next to the toggle. Clicking it turns the toggle on. It is only a suggestion, so you can ignore it and add the item as is.
  • Turn on Always isolate for a path in the Isolated runs section of Settings. The toggle then starts on when you pick that path. If you turn it off before adding, that item does not run isolated. Items that reach that path without the add bar, such as recurring schedule runs, run isolated.
  • A Queued card that hasn't started has an Isolate or Don't isolate button. Running and finished cards can't be changed.
  • Turn on Run isolated by default in a recurring schedule rule and the items that rule creates run isolated.
  • Cards for isolated items carry an Isolated badge.

Worktree folder and branch

  • The worktree is created beside the repository folder as ../{repository folder}-cmdq-{item number}. For example, item 12 in ~/work/app runs in ~/work/app-cmdq-12.
  • The branch is named cmdq/item-{item number} and starts from the current HEAD of the original repository.
  • When the run ends, CmdQ commits whatever is left in the worktree as [cmdq] item #number. The Files to copy and the paths in Leave out of auto-commit below are left out of that commit.

Preparing each path

A new worktree has neither the files listed in .gitignore nor installed dependencies. Fill both in per path in the Isolated runs section of Settings. Pick a path from the tabs (folder names) at the top of the section to see only that path's settings; the full path appears on one line under the tabs (shortened from the start when long, shown in full on hover). Folders with the same name get their parent folder's name added. Then click Save.

Check at startup

An isolated worktree can be left behind if CmdQ quit before you handled it. At startup CmdQ looks for these worktrees and removes only the handled ones without changes. Ones that still have changes, haven't been handled, or have no record in this app stay. Handle the unhandled ones from their cards; only handled ones that still have changes, ones with no record in this app, and ones whose card has no worktree record are counted in a "Leftover isolated worktrees" notification. You can open those folders next to the repository and clean them up yourself.

Reverting a regular item

Items that are not isolated can also go back to how things were before they ran. Turn on Save a checkpoint before each run under Queue execution in Settings (off by default), and CmdQ records a git checkpoint (HEAD plus uncommitted changes) right before each path item runs. Revert to before this run on a finished card asks for confirmation, then restores the path to that checkpoint.

  • Before reverting, the current state is backed up with git stash. The backup name appears in the completion message, and you can find it in git stash list to recover it.
  • Changes made by other tasks in the same path can be reverted too.
  • If untracked files are too many or too large for the checkpoint limit, the item runs without a checkpoint and a notification appears. That item can't be reverted.
  • Reverting is refused while an item in the same repository is running, waiting in the auto queue, waiting for a limit reset, or has an interactive terminal open. While a revert is in progress, new terminals can't be opened for regular (non-isolated) cards that use that repository. Isolated cards and reattaching to a terminal that's already open are not affected.
  • Untracked files that existed before the run are part of the checkpoint and come back with their pre-run contents. Files ignored by .gitignore are left alone.
  • If you switched branches or rewrote history (reset, rebase, etc.) after the checkpoint was saved, nothing is reverted. The confirmation shows how many commits came after the checkpoint, and after reverting they stay under refs/cmdq/revert-backup/… so you can recover them with git.
  • The backup ref holding the pre-revert HEAD is kept even when there was nothing to back up, and its name appears in the completion message. It is never deleted automatically; remove it with git update-ref -d <ref> when you no longer need it.
  • Isolated items don't have this button. Choose Discard to undo their result.

Attachments

Attach the files, links and memos a task needs. Attachments belong to a session, and every command in that session shares them.

Adding

  • In the add bar: File, Link or Memo. They're saved with the new command when you add it.
  • On a card: open 📎 and add from the drawer.
  • Drag files from Finder onto the add bar or an open drawer.
  • Links must start with https:// or http://. Memos are Markdown.
  • 📎 in a bookmark row or a terminal works on the same session, even after the card is deleted.

Using them in a command

Attachments reach claude only when the command contains a marker. [첨부] passes every attachment in the session. [첨부:3] passes attachment 3 only. The marker word is Korean in every UI language. Type it as shown.

  • Text files and memos open as Markdown or Raw text. Images and PDFs preview in place.

Project materials

Keep documents, folders, memos and links for each project tab (path), and let claude answer or work from them. Attachments belong to a session; materials belong to the tab path, so every command and terminal on that path shares them.

This feature is a Pro candidate and carries the Pro Preview badge. Until the official 1.0.0 release, it's free for everyone.

Collecting materials

  • The materials bar for the active tab sits at the right end of the scope bar above the queues. It shows the tab name, the number of materials and, when something awaits review, an N awaiting review pill. Project tabs show only the name and ×.
  • Click Materials (⇧⌘M) in the materials bar to open the materials drawer for that path on the Materials tab. The drawer sits on the right without covering the queues; the Pro Preview note is in the ⋯ menu next to its title. Switch with the Chat, Materials N and Links N tabs at the top. The numbers are the number of materials and linked modules, and when link suggestions are waiting they show together, like Links N · N suggested.
  • Add materials from the single + Add ▾ menu: File, Folder, Memo or Link. While there are no materials yet, the empty list explains this.
  • The list is grouped into memos, files, folders and links. Click a group header to collapse it. Click an item to open that material's detail screen in place of the list, and go back with ← List. The detail screen gives most of its space to the viewer, and editing the summary and keywords is under the collapsed Summary · keywords · source. Per-material actions such as re-saving, and deleting one material at a time, are in the detail screen's ⋯ menu; to delete several at once, use Select at the top of the list. Materials changed without approval carry an Awaiting review pill, and materials without a summary carry No summary.
  • Click Select at the top of the list to show a checkbox on every row; clicking a row then toggles its selection instead of opening the detail screen. Select all picks only the rows you can see and skips rows in collapsed groups. Rows you already selected inside a collapsed group stay selected and are counted and deleted too. The count shows as N selected, and Clear selection empties it. Delete selected opens a confirmation that shows how many materials will be deleted, the count for each kind, and how many sub-pages saved with links go too; nothing is deleted until you click Delete. Delete selected is disabled while nothing is selected, and it deletes up to 100 materials at a time. If some can't be deleted, the deleted ones leave the list, the rest stay selected, and their names and reasons appear inside the drawer. Turn selection mode off with Done or Esc to clear the selection; clicking a row opens the detail screen again. In selection mode, Space selects or deselects a row, and Delete or Backspace opens the delete confirmation. Esc closes an open ⋯ menu first, then turns selection mode off. Space, Delete and Backspace do nothing while the cursor is in an input field.
  • Two tabs share materials only when their paths match exactly. A trailing / is ignored. A tab on a subfolder, or another worktree of the same repository, has its own materials.
  • Closing a tab keeps its materials, and they come back when you open a tab on the same path. You delete materials only from the materials view.
  • A project can have up to 100 materials. A folder counts as 1, however many files it holds.
  • Project memos are also saved as files under memos/ in the materials folder, so claude can read them. The memo in the materials view is the source; when you edit a memo, CmdQ updates its file to match.

Folder materials

  • Under + Add ▾ → Folder, type exclude patterns (optional) and pick a folder with Choose folder. CmdQ copies the folder, so the original is never touched.
  • Symbolic links are skipped, not followed. .git, node_modules, target, dist, build, .DS_Store, .venv and __pycache__ are always left out, at any depth.
  • Exclude patterns use gitignore syntax, for example *.log or build/.
  • A copy can be up to 500 MB after exclusions. A larger folder is stopped before copying starts, and CmdQ asks you to add exclude patterns or add the folder in parts.
  • When the original changes, open the folder material and click Re-import. CmdQ then reports how many files changed, were added and were removed.
  • CmdQ remembers the exclude patterns you typed when adding the folder and applies them again on re-import. If you typed none, only the default exclusions apply.
  • If adding a folder skipped symbolic links or files it couldn't read, CmdQ tells you how many, for example "Folder added. Skipped N link(s) and N unreadable file(s)."

Links and linked subpages

  • Adding a link runs on its own screen that starts from + Add ▾ → Link, in the order Address → Collect → Choose. Collecting sub-links and the Choose pages to save step below both happen there, and you return to the list when it ends.
  • On a link material's detail screen, Esc goes back to the list even when your input is inside the web page; press Esc again to close the drawer.
  • Like attachments, link materials open in the in-app web view with your sign-in, and page text is saved only when you ask (Attachments). Text saved with Save text in the link's web view also goes into the materials folder, where claude reads it.
  • Turn on Also save linked subpages when adding a link, and CmdQ follows links on the same origin (same scheme, host and port), nearest first, until no new links turn up. Webview collection has no depth limit, and pages load one at a time.
  • Collecting needs the link's web view, so when you start, CmdQ opens the link in the web view first and then begins.
  • When you start collecting and Claude Code has an MCP server that can take that address (for now, a GitHub server for GitHub issue, PR, and file addresses), the collect panel shows “Auto: collect with MCP · server name, and hand pages it cannot fetch over to the webview” and a Collect with the webview only checkbox. The box is off by default; turning it on starts with the web view. The app knows servers only from the names and status that claude mcp list reports, and it neither reads nor stores MCP tokens, credentials, or config files. Claude Code and the MCP server handle authentication. If the matching server needs authentication, it says “MCP · server name needs authentication” and collects with the web view only. With no matching server, or if the list can't be read, it starts with the web view without asking. Collecting starts only when you click Start collecting, and Cancel closes the screen.
  • When Collect with the webview only is off (MCP), enter a Depth (1–10). The default is 3. CmdQ follows links in page text only that deep from the starting address, and if links were skipped because of the depth, it says “N links were not followed because of the depth limit”. Webview collection has no depth limit. The 500MB size limit and the 5,000 address limit are the same for both methods.
  • For every page, MCP collection runs a collection-only claude that is allowed exactly one read tool of that server. That is why you see “MCP collection runs claude for every page, so each page costs a claude run”, and it counts toward your usage limit. A GitHub issue's text and its comment list are fetched separately, so one issue takes two runs. Turn off Also fetch comments (on by default) on the start screen to fetch the text only, in a single run. These runs load your hooks and CLAUDE.md; the app runs them in an empty folder outside any repository and saves only the raw text the tool returned, not the model's answer. Collected text is saved in the materials folder as .md with a header that records the original address, author, update time, and how it was fetched. Ask materials and summary runs still block your MCP servers.
  • In MCP collection, links inside the same repository are followed by default. GitHub links to other repositories appear only as “Out of scope” candidates, and only the ones you check in the other-site link list below are fetched. Links MCP could not open are gathered under “Links MCP could not open (only the ones you choose are fetched with the webview)”, and you can pass the ones you choose to webview collection with Fetch with webview.
  • When webview collection lands on a sign-in page, it pauses and says “Collection paused because a sign-in is required. Sign in on the open page, then resume.” The address appears next to Sign-in page:. If the page redirects to a sign-in server on another host (SSO), collection opens the page once more so the web view shows that server's sign-in screen, then pauses; that server's address appears next to Sign-in page:. Sign in yourself in the open web view, then click I signed in, resume; collecting continues from the page that was redirected, with the same limits and visit history. The app never reads or stores passwords or cookies. A page that MCP collection could not reach because of authentication is only marked Sign-in required in the tree.
  • Each row of the received-page tree shows how the page was fetched (Webview or MCP · server name), how it was found (start, body link, child list), depth N, and an Out of scope mark.
  • Only one subpage collection runs at a time across the app. If you start one, or add an other-site link to a finished collection to run it again, while another is running, you're told to start again after it finishes or you stop it.
  • While collecting, you see pages saved and queued and the time elapsed. Stop ends it. Links whose address path or query contains words such as logout, signout, delete, remove, approve, reject, unsubscribe, cancel, reset, archive, publish, checkout or purchase can change state, so they aren't followed. Words such as accept, verify, subscribe, vote, submit, pay, order and enable are checked in the path only, so sort and setting values in the query (such as ?order=desc) aren't judged. When in doubt CmdQ leaves a link out, so ordinary addresses such as /blog/archive or /Headers/Accept can be skipped too.
  • A collection that starts from a public address doesn't follow links to localhost, private IPs (10.x, 192.168.x and so on) or link-local addresses. A collection that starts from an internal address has no such limit. CmdQ also resolves names and skips links that lead to a private address, as well as dotless names and internal suffixes such as .internal. If a name can't be resolved the link may be skipped for a moment, so collect again shortly after. It can't catch a name that changes to another address at connection time. If a page moves to a host CmdQ hasn't seen while collecting, that page can stay in the tree as Not received. If the start address redirects to another address, enter the address it lands on as the start address.
  • If you close the materials view or switch to another project's materials while collecting, collecting stops. The received pages are kept, and if you reopen that project's materials view before restarting the app, Choose pages to save comes back.
  • When collecting ends or stops, Choose pages to save shows the received pages as a tree. Uncheck the ones you don't want and click Save chosen pages. Close without saving keeps nothing.
  • If you leave a stopped collection (including one stopped by closing or switching the materials view) without saving or closing it, its received pages are cleared when the next collection starts, once 10 minutes have passed since it stopped. After that it can't be reopened.
  • Links to other sites are listed separately, and only the ones you pick are collected with Collect. Each picked link is followed to the end within its own origin, by the same rules.
  • If Collect on an other-site link doesn't start collecting (the collection was stopped or ended by an error or limit, or the link was already added), the view doesn't switch to collecting and you see "Collection did not start from this link."
  • The copy of one link material can be up to 500 MB. At that size, collecting stops and shows the pages received so far.
  • Webview collection has no depth limit, but separate limits protect resources. When one collection has queued or visited 5,000 addresses, it stops and shows the pages received so far. This shows a different notice from the 500MB size limit (“Stopped at the address limit of 5,000. Review the pages received so far”). Addresses longer than 2,048 characters aren't followed, and at most 500 other-site link candidates are listed.
  • If adding an other-site link to a finished collection hits this address limit, you see “The address count limit (5,000) was reached, so this link cannot be added. Review the pages received so far” and the pages received so far are shown.
  • You can Collect only other-site links that turned up during collecting and are on the list.
  • Open a link material and click Save again to collect from the first link again. CmdQ compares it with the last save and shows how many pages changed, are new and were removed. Saving replaces all previously saved subpages with the newly chosen ones, and pages missing this time are dropped. If saving fails, the last save stays as it was. CmdQ never re-collects on its own.

Suggestions and approval

claude doesn't edit materials directly. It writes suggestion files to _proposals/ in the materials folder, and CmdQ tells it to write at most 3 per run. Each suggestion shows up in the decision inbox as a Material suggestion card, and nothing in the materials or index.md changes until you approve. Details are in Material suggestions in the decision inbox.

Materials changed without approval

Queued runs start claude with --dangerously-skip-permissions, so claude can ignore its instructions and edit files in the materials folder. CmdQ can't prevent this; it finds and reports such changes afterward.

  • CmdQ keeps a hash and a copy of the approved content of every material file. The copies sit outside the materials folder, where claude can't open them.
  • CmdQ compares the materials folder when a queued run with [자료] ends (headless, or an interactive terminal opened from that card), when an Ask materials answer finishes, and when the app starts. Terminals reclaimed by a usage limit, and terminals that end because you delete their card, are also compared right when they end. Deleting a running headless [자료] card still compares the folder when the run ends.
  • CmdQ also compares the materials folder before it changes materials itself (adding, deleting or editing materials, re-importing, saving a collection, approving a suggestion). So if you change materials while a run is going, files claude edited are put up for review instead of being overwritten by CmdQ. Re-importing a folder or saving a collection again stops without replacing the copy if that material has changes waiting for review. Handle them in the Decision inbox, then try again. Approving a suggestion also compares first, including the index.md CmdQ has not written yet, so an index that claude edited directly is put up for review.
  • If a file changed outside _proposals/ (edited, added or deleted, including direct edits to index.md), a Material changed without approval card appears in the decision inbox. Each file shows Changed by and Changes. Changed by points to the run that first found the change and is not overwritten by later checks. A queue card run shows as Item #number, and an interactive terminal without a card as Interactive terminal (first 8 characters of the session ID). A change found when the app starts shows While the app was closed (found at startup). Long stretches of unchanged lines in the diff are folded into "… N unchanged lines".
  • Comparisons and CmdQ's own changes run one at a time per project. If they overlap in the same project, the later one waits for the earlier one to finish.
  • When comparing, a file whose size and modified time match the last approved state isn't read again and counts as unchanged. So a file whose content changed while its size and modified time stayed the same isn't caught by this comparison.
  • A card for a large or binary file shows only the size instead of the changes, but the card is tied to the file's content at that moment. If the file changes again after you saw the card, Revert and Keep aren't applied and the card comes back with the current content.
  • A file that can't be read or is too large (over 256 MB) is marked Cannot check (unreadable or too large), and the other files are still compared.
  • Pick Revert or Keep for each file. Revert restores the last approved content and deletes added files. Keep accepts the current content as approved. Keeping a memo file under memos/ also changes that memo's content to the file's content. Keeping the deletion of a memo file removes that memo from the materials. CmdQ never picks for you.
  • If the memo changed in CmdQ in the meantime (a memo edit or an approved append suggestion), keeping its memo file is refused with "The memo changed in the meantime, so this can't be kept. Choose revert or check the memo."
  • Until you pick, the file stays Waiting for you and the queue keeps running. In the meantime, runs with [자료] and Ask materials also get a line saying there are changes awaiting review.
  • CmdQ doesn't overwrite a file waiting for review (including index.md and memo files) until you pick Revert or Keep. While index.md is waiting, index updates are put off, and the index is rebuilt after you pick.

Interactive terminal

A real claude session inside CmdQ, for work that needs back-and-forth.

Opening one

  • Run interactively on a card.
  • The Interactive target in the add bar (⌃3). New session, no card.
  • Session target, then ▶ Terminal. Reopens that session.
  • ▶ on a bookmark, or a row in the background terminal list.

If the session is open in another live terminal, CmdQ reattaches to it instead of starting a second claude.

Taking over a session the queue is running

Opening a session with ▶ Terminal, a bookmark or the terminal list while the auto queue is running it asks first: stop the queue run and hand the session to an interactive terminal? The question also says how many background tasks in that session will be stopped. Confirm, and the run stops, the terminal opens, and the item is marked done with a Handed off badge. Cancel changes nothing. From a card, you get no prompt. CmdQ tells you to open it again after the run finishes.

Header

  • Click the project name to copy the project path. Click the session label to copy the full session ID.
  • Run in background closes the window and leaves claude working. The card shows Terminal running; click it to reattach.
  • Terminate stops claude and ends the session.
  • ☆ bookmarks the session, even without a card.
  • 🕐 opens this session's question history over the terminal. Pick a question to read its reply; close it (×, Esc or a click outside) to return to the same terminal and keep typing. It reloads on every press. It stays disabled until the session id is known. Answers you sent from the decision inbox are in this list too, as questions you typed. A terminal the inbox opened to send an answer has it enabled from the start.
  • 📎 opens the session's attachments. Add, delete, reorder, edit memos or drop files, as in the drawer. Insert into terminal or Insert all pastes them into claude's input line; you press Enter yourself.
  • Snippets opens saved commands in two lists, Shared and This path. Pick one to fill the edit box, then Apply to paste and run it. Edits there apply to that run only. ⇧⌘P toggles the panel and jumps to the new-snippet form.

Background terminal list

N terminals in the header (⇧⌘T) lists live terminals and terminals waiting for a reset. Click a row to open it. Each row also has 📎, ☆, ✎ Rename and Terminate. ✎ Rename on a live terminal's row sets the name shown in the list. Press Enter to save or Esc to cancel. Once a terminal has a session, the ✎ next to the title in its window header renames it too, and a name changed there shows up right away in an open list. Saving and canceling work the same as in the list. The same name appears on the Waiting for reset row, but you can't change it there. Clear the name and confirm to go back to the original title. The name stays after you restart the app. It changes only the displayed title; the queue card's command, the bookmark alias and the path shown stay the same. Terminate all asks for a second click. A terminal opened from the list returns to the list with ⌃←. ⌃→ takes you back to that terminal. Pressing ⇧⌘T while an interactive terminal is open works like Run in background: a terminal opened from the list goes back to the list, and one opened from a card or the add bar goes back to the main window. It does nothing while another window, such as Settings, is open over the terminal.

While you work

  • When output stops for 8 seconds, you get a Waiting for input notification, but only for terminals with 🔔 on in the terminal header. A terminal opened from a queue card follows that card's 🔔. It isn't sent while you're looking at that terminal in the main window. Change or turn off the delay with Interactive input-wait alert (Notifications).
  • ⌘+click a URL to open it in your browser.
  • Mod panels take mouse clicks only with claude's fullscreen renderer: run /tui fullscreen in claude, or start it with CLAUDE_CODE_NO_FLICKER=1. With the default renderer, claude ignores the mouse.
  • Emoji count as two cells, as in claude, so tables and panels stay aligned. For a wider terminal, set Terminal window width to Full width.
  • When you come back from another app or reopen a terminal, CmdQ has claude redraw the screen. If the screen still goes blank, press ⇧⌘D to save a diagnostics file to diagnostics/ in the app data folder and attach it to a bug report. It contains terminal output, so read it before sharing.
  • If a usage limit hits, the terminal closes and resumes after the reset (Usage limits).

Decision inbox

The decision inbox gathers the questions claude stopped on across your sessions, so you can answer them in one place. When a question is waiting, a ? Decide N badge appears to the left of 🔍 in the header. N is the number of questions waiting for you.

What it collects

  • Interview questions, where claude shows a list of choices (AskUserQuestion). These cards are marked Interview. claude opened in an interactive terminal in CmdQ gets an instruction to ask with this question tool, not in plain text, when it needs a decision from you.
  • Questions claude asked in plain text before stopping are always collected too, including questions that ask what you want, such as "What can I help you with?". These cards are marked Text and Guess and show the end of claude's last reply. CmdQ looks at the shape of the whole reply, not only its last line, so requests to choose or decide are caught even without a question mark, such as a "Decisions needed" section in the middle, a list of options, or a note on how to reply. Replies in English and Korean are both checked. Detection is still a guess, so some cards may not be real questions. Clear those with Dismiss.
  • CmdQ checks every 15 seconds and looks at every session changed in the last 24 hours. Sessions you didn't open in CmdQ show up as cards too.
  • New decision requests trigger a notification. Requests already waiting when CmdQ starts, material suggestions, and changed-material cards don't. Card 🔔 doesn't apply here; the Decision requests setting does (Notifications).
  • Sessions the auto queue ran are checked with broader rules. See Queue run questions below.

Queue run questions

  • The auto queue runs claude headless, so interview question prompts never appear. Queue runs therefore get an instruction, whenever they need a decision from you, to end the reply by first writing the questions and choices in Markdown and then repeating them in a decision block (JSON) in a fixed format. You can read what is being asked in the response view or an interactive terminal, and the inbox builds the card from the block. A queue run session is one the auto queue has run headless at least once. A session first opened from a queue card in an interactive terminal follows the same rules as any other session.
  • When a reply ends with a decision block, its questions and choices show up in the inbox as they are, and the card is marked Queue question. Choices claude recommends are marked Recommended, but they aren't picked for you, so choose yourself. The summary written before the block is shown on the card too, but only up to the first question line, so each question appears on the card once. A card splits up to 10 questions. With more than 10, they are listed in one numbered question that you answer by typing. Several questions or a table asked in plain text are also split up to 10, and beyond that become one question you answer by typing. Interview questions follow the question tool limit of 4.
  • If a queue run ends by asking in plain text without a block, CmdQ still guesses it is a text question and collects it, looking for several questions and recommended marks too. These cards are marked Guess, and a choice that includes (Recommended) is also marked Recommended. Conditional closings such as "let me know if you need anything else" aren't treated as questions.
  • When there are several questions, you answer them step by step, as with interviews. For text questions, only the answers are sent, one per line as A1: …, A2: …, without quoting the questions.
  • Like text questions, queue questions aren't sent to an interactive terminal. If the session is open in an interactive terminal in CmdQ, the card says "Queue questions aren't sent to an interactive terminal. Answer in that terminal".
  • Session history and the response view don't show the decision block. Only the summary, questions and choices written before it remain. If the reply is only a block, or the block is one the inbox can't read, it is shown as is. The live log you watch during a run shows the block as written.

Answering

  • Click the badge or press ⇧⌘C to open the inbox under the badge. Press the key again, press Esc, or click outside to close it. When no decisions are waiting and the badge is hidden, the key does nothing. Change the key in Shortcuts. Hover over the badge to see the current shortcut. If none is set, it says "No shortcut — you can set one in Settings".
  • Click a card's title row to expand or collapse it. ⌘↑ and ⌘↓ move the expanded card up and down.
  • The top of an expanded card shows the Project path the question came from and the Command that led to it. Hover over a cut-off path to see all of it, and use Show all to read a long command in full.
  • Pick a choice or write in Type your own. Questions that allow several answers show checkboxes. If a choice has a Preview, expand it to read it.
  • When claude asked several questions at once, each gets a step button, and N questions left shows how many still need an answer.
  • An interview can be sent only after every question is answered. Text questions and queue questions can be sent once you answer one of them. Unanswered questions are left out, and the reply ends with a line such as 미응답(unanswered): Q2, Q3 so claude knows which ones were skipped.
  • Once the card can be sent, Will send shows the exact text that goes to claude. Check it, then click Send or press ⌘Enter. A sent card folds into a Sent ✓ line and then leaves the list.
  • For sessions that aren't open anywhere, the card shows Send to queue where Send would be. That button, or ⌘Enter, puts your answer in the auto queue without opening a terminal. Hover over it to see "Sends as a resume task · waits in the queue". A queued card folds into a Queued ✓ line and then leaves the list. To continue in an interactive terminal right away, click Send to terminal next to it. See Where the answer goes below for details.
  • Later (30 min) puts the card away for 30 minutes. If only snoozed decisions are left, the badge reads 0 · later N, and the badge and ⇧⌘C still open the inbox.
  • Dismiss removes the card without sending anything to claude.
  • ↗ Terminal closes the inbox and opens that session in an interactive terminal. If the auto queue is running the session, CmdQ asks before taking it over.
  • ↩ Decisions N in the interactive terminal header opens the inbox on top of the terminal and leaves the terminal as it is. Choices and text you entered on a card stay there when you close and reopen the inbox.
  • The inbox opens on top of the attachment and schedule drawers, the interactive terminal and session history. Only Settings and About appear above it.

Notifications

Notifications arrive the way you pick in Settings › Notifications › Notification style. System only shows macOS notification banners. Popup opens a window in the top-right corner with cards stacked in a list, and Top widget shows a band at the top center of the screen. With Popup + widget, the same alert shows in both.

  • What gets an alert: Done, failed, waiting-for-reset, and waiting-for-input alerts come only from cards and terminals with 🔔 on, and that includes system banners. Turn 🔔 on or off with the 🔔 button on a card or in an interactive terminal's header. For a terminal opened from a card, the card's 🔔 changes too. New cards start with the 🔔 default from Settings. Cards with 🔔 on show a 🔔 Alert badge. Decision requests don't use 🔔; they follow Decision requests.
  • Where 🔔 carries over: the next step in a chain inherits 🔔 from the step before. Runs created by a repeat rule (including Run now) follow the rule's Alert when done 🔔, or 🔔 on new cards if the rule leaves it unset. You can still change each created card with its own 🔔. An item that resumes a session after you answer in the decision inbox inherits that session's 🔔: the session's own 🔔 if you turned it on or off, otherwise the session's last card 🔔, otherwise 🔔 on new cards. An interactive terminal without a card also follows 🔔 on new cards until you turn its 🔔 on or off.
  • Alerts that always come: reclaiming terminals at a limit, the alert that two runs changed the same file, rules turned off after failures, app updates, and isolated-run notices arrive as system banners whatever the 🔔 and per-event settings, unless the style is Off.
  • Popup and widget styles: done, input-wait, and decision alerts go only to the popup or widget, not to system banners. If the popup or widget can't be shown, a system banner is sent instead.
  • Alert titles: if you gave a terminal a name, the alert title shows that name instead of the path. Renaming applies from the next alert on, and cards already shown stay as they are.
  • Card buttons: Go to terminal opens that item's or session's terminal in the main window. It takes the same path as running a card interactively, so it attaches to a live terminal or resumes the same session if it has ended. Decision cards have Answer in decision inbox. Hide clears only that card.
  • Widget: the band shows the pending count and the latest alert, with the card list below. Collapse leaves only the count, and clicking the count expands it again. Hide all clears every card in both the popup and the widget.
  • Hidden cards: a hidden alert doesn't come back for the same event. CmdQ keeps this in memory only, so it resets when you restart the app. Cards for decisions answered elsewhere or cleared in the decision inbox, and cards for a session where you started new input, close on their own.
  • While you're looking: if the main window is in front and you have that terminal open, its done, input-wait, and decision alerts aren't sent.
  • First launch after updating: earlier versions alerted on every finished card, but new cards now start with 🔔 off. Existing users see a one-time "Per-card completion alerts" notice on first launch. Turn on 🔔 for new cards makes every new card alert as before, and Keep as is leaves your settings alone. The notice doesn't show if Notification style is Off, or on a fresh install.

Changing a shortcut

In Settings › Shortcuts, click a key field and press the new combination. Clear sets it to None. Default restores the original.

  • A combination needs ⌘, ⌥ or ⌃.
  • A combination already in use is refused with the name of the action that has it.
  • If you had already assigned ⌘K to another action, Search starts as None. Assign it a combination in Settings to use it.
  • You can't assign: the app menu keys (⌘C ⌘V ⌘X ⌘A ⌘Z ⇧⌘Z ⌘Q ⌘H ⌥⌘H ⌘M ⌃⌘F), the submit keys (⌘Enter ⌃Enter ⌃⌘Enter), and ⇧⌘D (save terminal diagnostics).

When shortcuts work

  • Only while the CmdQ window has focus.
  • In a text field, only combinations with ⌘, ⌥ or ⌃ fire.
  • With a full-screen view open (terminal, history, settings), only Settings, Search, Add snippet, Back and Forward work. Decision inbox also works over an interactive terminal or session history.
  • Terminals closes the terminal list when it's open. With an interactive terminal open, it puts the terminal in the background like Run in background: a terminal opened from the list goes back to the list, and one opened elsewhere goes back to the main window.
  • Search's key goes to CmdQ, not claude, even while an interactive terminal has focus.
  • Forward only works when you press it right after Back. Pressing any other key in between (typing in the shell or the command box, Esc, another shortcut) clears the Forward history, and in an interactive terminal ⌃→ then goes to the terminal, so word movement still works. The same happens when there's nothing to reopen or the terminal has ended. Closing a window or clicking a tab with the mouse keeps the history.
  • If macOS Mission Control uses ⌃← for "Move left a space", it gets the key first. Assign Back to something else.
  • The same goes for ⌃→ and "Move right a space": if it's on, macOS gets the key first. Assign Forward to something else.

config.toml

Settings live in ~/Library/Application Support/com.doitasap.cmdq/config.toml. A few keys exist only there.

  • Quit CmdQ before editing. Saving in Settings rewrites the whole file and drops edits made while the app was running.
  • Out-of-range values are clamped to the nearest limit, and CmdQ tells you which ones.
  • A file that can't be parsed is moved to config.toml.bak, and CmdQ starts with defaults.
