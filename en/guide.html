CmdQ user manual

This manual covers the current version of CmdQ. Names in bold match the English UI. New to CmdQ? Install it first with Get started on the home page.

Queued tasks run Claude Code with --dangerously-skip-permissions. Claude Code will read, write, and delete files and run commands in the target folder without asking you first. Review what you queue, keep your work under version control, and use this app only on folders you are willing to let it change. You are responsible for the results of the tasks you run.

The window

Header

  • Usage is always shown as text on the right of the header, like "5h 42% · Week 18% · Reset 1:12:03". A thin bar under the 5h and weekly numbers shows the same figure and turns amber above 80%. These are the 5-hour window and the Weekly limit.
  • Reset counts down to the next 5-hour reset and is underlined for the last 10 seconds. Hover the usage text to see the time left until the Weekly reset.
  • When the weekly limit is used up, the label changes to Weekly limit · resumes and the queue waits for the weekly reset.
  • Unreadable means the last usage check failed. N/A means your plan doesn't report that value.
  • The tools at the right end are 🔍 Search (⌘K, finds Search questions across sessions; see Progress and history), Bookmarks, Terminals N (only while background terminals exist) and Settings. Switch between light and dark in Settings › General › Theme, not in the header. In a narrow window the labels hide and only the icons stay; hover an icon to see its name.
  • Between the usage and the tools, each kind of thing waiting for you gets its own badge, hidden at 0. When questions are waiting for your answer, a blue Decide N badge appears. Click it or press ⇧⌘C to open the Decision inbox. When claude has posted task proposals, a Proposals N badge appears next to it. Click it to open Proposals. With the inbox on, there is also an Inbox badge (Inbox).
  • A badge opens its list right below itself, one list at a time. All three lists have the same header: title, count and ✕. Close with Esc, a click outside, or ✕.
  • In a narrow window (960 px or less) the header takes two rows: the logo, tabs and tools on the first, usage and badges on the second. Nothing is hidden.

Project tabs

Each tab is one project folder. Click + Folder (⌘O) to open one. A tab shows only the items for its path, and the add bar uses that path. Switching tabs resets the add bar to the Path target and the To Do queue.

Closing a tab (⌘W or the tab's ×) deletes nothing. Auto queue items for that path keep running. Drag tabs to reorder them.

Turn on Show all (⇧⌘A) to see items from every open tab, grouped by path. Dragging cards is locked while it's on.

Clear completed in the auto queue header deletes every completed card on screen at once: all open tabs with Show all on, otherwise only the current tab. Cards handed off to a terminal, cards with an open interactive terminal, and cards with unfinished child commands are kept.

Queues and item numbers

Below the add bar are two lists: Auto queue and To Do. In the auto queue, the circle on the left of a card is its place in line. It turns into a pulsing light while the item runs and a ✓ when it's done. The #12 chip is the item's ID. It never changes, and notifications use it to name the item.

Menu bar icon

CmdQ keeps running in the menu bar after you close the window, and the auto queue keeps going. Choose Quit (⌘Q) in the menu to stop it.

Click the icon for a menu showing your plan, both usage figures with a usage ring, each reset countdown right below its figure, a line with the check interval and last update time, and an auto queue summary. Each row has a small icon, and the usage ring fills in 5% steps. Below that: Refresh usage, Open window, Settings…, Open log folder, a Help & Support submenu and Quit. Help & Support holds About, Check for Updates…, Report a bug, Request a feature, Support CmdQ — Star on GitHub and Sponsor…. Report a bug opens a prefilled GitHub issue in your browser with the app version, macOS version and CPU type. Nothing is sent until you submit it.

CmdQ checks for a new version about 20 seconds after launch and every 6 hours after that. When one is available it asks first, and only downloads, installs and restarts when you choose Install and Restart. If auto queue tasks are running or interactive terminals are open, the prompt says they will be stopped by the restart. A version you put off with Later isn't offered again until the app restarts; in the meantime you can install it from Check for Updates…, which also tells you when you're already up to date.

Ideas tab

The Ideas tab in the header (⌘1) is where you talk to claude about a topic without a project. The app opens on the Ideas tab. Chats are split by topic, not by path, and run in a dedicated folder under the app data. The input box stays at the bottom of the window.

Layout

  • The screen has three columns: the chat list on the left, the chat in the middle and a rail on the right.
  • From top to bottom the rail shows Sources, the progress route (four stops: Chat, Proposals, Queue, Results) and Attachments.
  • In a narrow window the rail folds away. Open it as an overlay panel with the Progress button in the title row.

Conversation

  • The chat looks the same as the chat in Project materials. Type a question and send it. The input box shows "What would you like to think through?".
  • There is no limit on the number of chats, and one chat keeps up to 1000 turns. A title is added automatically after the first answer.
  • Scroll to the top of the chat to load earlier turns.
  • If you hit a usage limit, the question you sent is put back in the input box.
  • Click a source chip under an answer, an attachment in a question bubble or a sent link to open it. Files and source copies open from the copy saved in the chat folder in the default app. Links open the original address in the browser.

Empty chat

  • A small logo sits at the top, with "Write a topic to start a conversation." below it.
  • Below that, Recent results shows up to 3 cards. Each card shows the status, a summary of the command and the title of the chat it came from. Click one to open that chat. When there are no returned results, this row does not appear.

Left panel

  • ＋ New chat opens an empty chat.
  • The list is grouped into Today, Yesterday, Previous 7 days and Older. Load more appears when there are more.
  • Search chats looks in titles and in the text of questions and answers.
  • Rename (F2) on a row changes its title. Delete asks for confirmation. Deleting removes the questions, answers and attachments, and can't be undone.
  • In the list, ↑ and ↓ move to the neighboring chat and Enter opens it.

Right rail

  • Sources: the sources the answers in this chat used, by name. The same source appears once.
  • Progress: the four stops on the vertical line are the group headings.
    • Chat stop: "N turns · last HH:MM".
    • Proposals stop: "In inbox N" shows how many proposals are left in the inbox, and the proposals waiting for approval are listed below. Click one to open Proposals.
    • Queue stop: counts by status, with the queue items listed below. Click one to go to that item in the Workspace tab.
    • Results stop: returned results are listed. Status shows in text (Waiting, Running, Done, Failed), not only in color, and for a finished item you can expand its Result summary.
  • Attachments: the files and links attached to questions.
  • Click a source or attachment to open it the same way as the chips in the chat. Files and source copies open in the default app, and links open the original address in the browser.
  • Under an answer, a mark shows the work sent from that answer. Click it to see it in the rail. With no items, the rail says "Progress and results of work sent to the queue from this conversation gather here."
  • When a queue item's status changes, the rail reads again right away, and it also reads every 10 seconds in case a change notice is missed. It does not read while the screen is hidden, and reads once when you open it again. Up to the 200 most recent items show.

Attachments

  • Use 📎 in the input box to pick files, or paste images and files, to attach them to a question. Attachments are saved with that chat.

Attaching links

  • Click 🔗 Add link at the top of the chat, enter an address and click Attach. At that moment CmdQ fetches that one page in the in-app web view and saves it as a copy in the chat's folder. Your next question is answered from that copy.
  • The top of the copy keeps url, title and saved_at. If the link changes or disappears later, the saved copy stays, so the chat keeps its evidence.
  • The chip shows the address and the save time ("Saved …"), and it goes along when you send the next question. Click the chip or a sent link to open the original address in the browser.
  • A link that needs sign-in is attached the same way. If a sign-in screen appears, sign in on the page that appears below, then click Try again. Cookies stay inside the web view and CmdQ does not store them anywhere.
  • Internal and private addresses, and addresses that change state such as logout or delete, are refused. Fetching waits up to 180 seconds. If the materials screen is fetching a link, attach again after it finishes.
  • If fetching fails or the sign-in expires, only an error shows under the chip and the chat carries on.
  • Text inside the copy is read only as evidence and instructions in it are not followed, and proposal blocks inside it are neutralized when saved. A long page is saved from the start only.

What claude can do

  • claude in an idea chat is read-only. It reads only files inside its dedicated folder and cannot change your repositories or files.
  • It can use web lookups (WebFetch and WebSearch) to read an address or search before answering.

Sending to the queue

  • There are three entry points, and all of them open the same sheet.
    • To queue → in the input area: the whole chat is the context.
    • Continue in queue under an answer: the chat up to that answer is the context.
    • Chat to queue in the chat toolbar: the whole chat is the context.
  • In the Send to row at the top of the sheet, pick the target folder with an open-workspace chip or 📁 Choose another folder…. You pick the path only in this sheet, and there is no separate path row above the input box.
  • The sheet fits the window without scrolling. The row with the add buttons is fixed at the bottom, and the context preview is collapsed.
  • The default templates made for materials chats are hidden. Only your own templates and Write my own show.
  • The resulting command has no [자료] marker (the materials marker). The chat goes into the command as a block for the earlier chat from the Ideas tab.

Putting results in the next question

  • Finished and failed items on the Results stop of the rail have a check box, and hovering shows Add to the next question's context. You can't check waiting or running items or a Deleted item.
  • When you check one, a "Result: …" chip (↩ Result) appears above the input box. Remove it with the chip's remove button.
  • When you send the next question, the command, workspace and result summary of each checked item are attached before the question as reference. Results of unchecked items are not added, and CmdQ never adds them on its own.
  • Sending the question clears all checks. To add the same result again, check it again. Switching to another chat also clears them.
  • Attached results are marked to be read only as evidence, and instructions in them are not followed. Proposal block formats inside a result are neutralized before sending.
  • A question is limited to 4000 characters, so a longer question leaves room for fewer results. If it overflows, later items are dropped first, and if one alone overflows, its end is cut. If the question leaves no room for context at all, only the question is sent.

Items from this idea

  • CmdQ records which idea a queue item or workspace came from: cards you accept in Proposals, queue items made with Continue in queue and the like, and workspaces opened by accepting Create workspace. Proposals that did not come from an idea and items made by schedules have no record. Child items in a chain count as coming from the same idea as their parent.
  • An item waiting for a usage limit to reset shows as Waiting, and hovering it shows "Waiting for the usage limit to reset".
  • The result summary is the last result from that item's run log, up to 2000 characters. If no result was found or it is empty, only the status shows, and failed items show no result summary.
  • If you delete an item from the queue, its row does not disappear but becomes Deleted item.
  • Deleting an idea chat does not delete the queue items or workspaces made from it. Only the link marks disappear.
  • One idea can produce several workspaces, and several ideas can link to one workspace. The Workspace tab has no mark for this link.

Usage limit

  • Idea chats use the same plan limit as the queue.
  • If either the 5-hour window or the 7-day window is at 90% or more, CmdQ holds the start of new queue items and the queue screen shows the banner "Near the usage limit, so new items are on hold. Running items keep going." Idea chats keep working.
  • If usage data is missing or stale, nothing is held. Held items run after the reset.

Skill autocomplete

Start a word with / and a list of your skills opens, labeled User, Project or Plugin. ↑ ↓ move the highlight, Tab inserts the skill, Esc closes the list. Enter does not pick a skill. It submits the text exactly as typed.

Images and paths

  • Paste an image and it shows up as [IMAGE]. CmdQ saves the image and hands its path to claude when the task runs. Backspace right after the marker deletes it.
  • Type @ to browse files and folders under the tab's path (or the session's folder for a session target). Tab or Enter inserts the path.
  • Type # to insert attachment markers. See Attachments.

Session target

  • Click Session, then pick from the session list for the tab's path. Each row shows how much of the context window that session has used. Sessions you started with Interactive carry an Interactive badge.
  • 🕐 History lists the questions asked in the selected session.
  • ▶ Terminal opens the selected session in an interactive terminal (Interactive terminal).

Interactive target

The text in the command box becomes your first message. An empty box opens a blank session. It won't open while the add bar holds pending attachments or attachment markers, because markers aren't expanded in an interactive session.

Changing a card's target

The small button next to a card's path or session chip switches the target: Switch to a session on a path card, Switch to a path on a session card. It isn't shown on running or finished items, on chain parents or on chain children.

Auto queue and To Do

Auto queue

Runs from the top on its own. Items paused at a limit go before newly queued ones once the limit resets.

To Do

A holding list. Nothing here runs until you promote it. Each card shows how long ago it was captured and warns when the context may be stale.

How many run at once

  • Within one path, the auto queue runs one item at a time, top to bottom.
  • Different paths run side by side. Auto-queue concurrent runs (default 3) caps how many paths go at once. Runs you start by hand and schedule runs don't count.
  • Concurrent runs per path (default 2) caps automatic plus manual runs in one path. Schedule runs don't count here either. At most one of them is automatic. Set it to 1 if your tasks edit files, because two runs touching the same file overwrite each other, or run the tasks that may overlap as isolated runs. A scheduled rule that edits files should turn on Run isolated in the rule.
  • Session targets also wait while their session is busy.

Moving items

  • ▶ To auto queue (Promote to the auto queue) on a To Do card moves it to the end of the auto queue. It starts when its turn comes.
  • Move to To Do on a waiting or failed auto queue card moves it back.
  • Drag a Queued or Waiting for reset card up or down to change the order. Running and finished cards stay put.
  • When two or more auto queue cards target the same session, they are grouped under one card, placed where the first of them to run sits; finished cards ahead of it move into the group. Replies you add with Send to queue in the decision inbox join the path card that first ran that session, starting with the first reply. The front card is the running one, otherwise the queued one that runs next, otherwise the one that finished running most recently. Path cards follow the same order. Click N more in session to show the rest below it; while the group is collapsed, the button also counts the running and queued cards inside (for example 1 more in session · 1 queued). Those cards can't be dragged. Dragging the front card moves the whole group and keeps its run order, even when the front card has finished, as long as the group still has a queued card; dragging any other card moves only that card. Either way, the cards you didn't drag keep their run order, and a card dropped right below a group doesn't become its child even if you drag it to the right.

A Running item keeps going as long as claude produces output. After 30 minutes with no output, CmdQ treats it as stuck, stops it and marks it Failed with "Stopped: no output for 30 minutes". Status lines that plugins print don't count as output. You can't change these two limits in Settings.

Chains

A chain is a parent task with follow-up tasks nested under it. Each child waits for the step before it, then runs in the parent's claude session, so it sees what the parent did.

#21 Refactor the auth module to use the new token store ~/work/api ↳ #22 Run the test suite and fix anything that broke ↳ #23 Draft a commit message for these changes

Making a chain

  1. Add the parent and the follow-up tasks to the same path, in the order you want them to run.
  2. Drag a follow-up card a little to the right while moving it (about 32 px). The drop slot indents.
  3. Release. The card becomes a child of the card above it. If the card above is itself a child, the new card joins the same parent as its next sibling.

Rules for nesting:

  • Both cards must use the Path target. Session tasks can't be nested; tasks for one session already run in order.
  • Chains go one level deep. A card that already has children can't become a child.
  • Only Queued or Waiting for reset cards can be dragged. This works in both the auto queue and To Do.
  • Dragging is locked while Show all is on. Pick a single tab first.
  • Use ▾ / ▸ on the parent to expand or collapse its children.

Recovering from a failed parent

  1. Click Run interactively on the failed parent. Its session opens in an interactive terminal with the earlier conversation.
  2. Talk claude through the fix, or send one message such as continue.
  3. Your first message marks the parent Done. The child resumes the parent's session, so it waits while a terminal still holds that session. Click Terminate on that terminal, and the first child starts on the next queue check.

Editing a chain

  • Detach from the chain (run standalone) on a child turns it into a normal item, placed after the rest of the chain. It stops waiting for the parent.
  • Stop (move back to queued) on any running item in a chain moves the whole chain to To Do. Finished steps stay Done. Promote the parent later and the chain picks up at the first unfinished step.
  • Move to To Do on a parent, or on a failed child, also moves the whole chain.
  • Delete on a parent deletes its children too, and stops any of them that are running.
  • Children have no 📎 button. They share the session's attachments, so add them from the parent card's 📎.
  • Children have no ▶, ⌘ or ☆ buttons of their own, except that a failed child gets Re-run and Move to To Do.

Example: build, then explain the failure

Run the production build and fix type errors ~/work/web ↳ If anything still fails, summarize the remaining errors and likely causes

The child reads the build output already in the session, so you don't need to paste logs into the second prompt.

Example: refactor, test, write the commit message

Refactor src/payments to remove the legacy client ~/work/api ↳ /test ↳ Draft a commit message for these changes. Don't commit

If /test fails, the commit message step waits. Fix the tests (or re-run the child) and the last step follows.

Usage limits and auto-resume

Claude Code has a 5-hour usage window and a weekly limit. Both are account-wide. When one runs out, CmdQ pauses all work and resumes it after the reset.

When you're close to a limit

  • If either the 5-hour window or the weekly limit is at 90% or more, CmdQ holds new queue items instead of starting them. This leaves the remaining usage for the idea chats you run yourself.
  • Items that are already running keep going to the end. Idea chats keep working too.
  • The hold applies to every queue item that is about to start, whatever its kind. That includes an item that delivers a decision-inbox answer and each run a recurring schedule creates.
  • While the hold is on, the notice above the queue changes to "Near the usage limit, so new items are on hold", with the window, its usage and the resume time in parentheses. If a limit has actually been reached, the usual reset notice shows instead.
  • Once usage drops after the reset, the hold lifts and waiting items run from the top.
  • CmdQ reads usage from the statusline. If the statusline isn't connected or its value is more than 10 minutes old, nothing is held.

When a limit is reached

  • CmdQ stops every running queue item, not only the one that hit the limit. Each goes to Waiting for reset.
  • Interactive terminals are closed (reclaimed). A terminal opened from a card puts its item in Waiting for reset. A card already handed off to a terminal is not run again by the auto queue, so it stays done. Its conversation shows as a Waiting for reset row in the background terminal list instead, and after the reset CmdQ reopens the same session as a background terminal.
  • A terminal with no card (opened with Interactive, ▶ Terminal or a bookmark) gets a row in the background terminal list: Waiting for reset · resumes HH:MM. Click the row to read the past conversation. Cancel resume keeps it from reopening.
  • You get a Terminal reclaimed notification for each closed terminal, and the menu bar icon gets a hollow dot.
  • The auto queue banner shows how long until queued items start again.

After the reset

  • Paused items run first, in the same claude session, with this prompt instead of the original command: Continue the work you were doing. Pick up from where it stopped and do not redo what is already finished.
  • An item that hit the limit before it had a session reruns its original command.
  • Card-less terminals reopen in the background with the same prompt. No window pops up. A toast says how many were resumed. Open them from Terminals N in the header.
  • After a weekly limit, the queue waits for the weekly reset, not the 5-hour one.

Statusline connection

On first launch CmdQ asks once whether to connect Claude Code usage. Connect points statusLine in ~/.claude/settings.json to a CmdQ wrapper, so usage updates faster and more accurately. Your existing statusline display stays as it is. Later keeps the periodic /usage checks only. Either way, CmdQ doesn't ask again for that Claude config folder, and Settings has no switch for it.

Recurring schedule

One rule creates a queue item at the times you set. The items it creates run in the same queue, in the same way, as items you add by hand.

Overview

  • The Ideas, Workspace and Schedule switch in the header changes the screen. The Schedule screen has two views, List and Calendar.
  • It is a free feature, and there is no limit on the number of rules.
  • Times follow this Mac's local time zone.
  • A rule creates its runs while CmdQ is running. Runs that passed while it was off are handled as you choose under Conditions.

Creating a rule

Click New rule to open the New schedule rule editor. The name, command, and path are required. The fields are grouped into Basics, Repeat, Run options, Conditions, and Instructions added to the command, all expanded.

When you open a saved rule, the editor has Rule, Runs, and Cleanup log tabs at the top and a Run now button in its header. Your unsaved edits stay while you switch tabs. Closing the drawer closes all three tabs, except that closing from a history tab while you have unsaved edits keeps the editor open and returns to the Rule tab. Run now creates one run from the saved rule and is off while you have unsaved edits, so save first. A new rule has no history yet, so it has no tabs and no Run now.

  • Name and Command. Add step turns the command into a chain. Each step continues in the same session after the previous one finishes.
  • Path. Choose path picks the folder.
  • Add to. Auto queue runs each created item from the queue right away. To Do only creates the item, and you run it yourself.
  • Alert when done 🔔. Applies to cards this rule creates (recurring runs, Run now, and later chain steps). You can still change each card with its own 🔔, and changing the rule later does not change cards it already made. If unset, it shows Follows default (on now) or Follows default (off now) and follows 🔔 on new cards. Click it to set On or Off, and Use default to go back.
  • Repeat and Conditions are described below.
  • Next 5 runs in the editor's bottom bar previews the next five times. The bottom bar stays visible while you scroll, so you see the result right away as you change the repeat, weekdays, or times. They are theoretical times with conditions not applied. With several times, each day lists its times in order, and the five are counted by run. A git ref update rule has no fixed time, so there is nothing to preview.

  • The date picker marks the days when the weekly limit resets with a dot.

git ref update

Choose git ref update under Repeat and the rule watches a repository ref instead of a clock. It creates a run only when the commit the ref points to has moved forward. The default ref is develop.

  • Base commit. When you create the rule, change its repeat type, turn it back on, or first check a duplicated rule, the current value is only recorded as the base and no run is created. Past history never becomes a run.
  • A run is created only when the ref moved forward. If the ref changed several times while the app was off, everything from the base to the latest commit becomes one run. Creating a run moves the base to the latest commit.
  • If the ref was rewound, or the change does not match the Only when there is a PR merge commit filter, no run is created and only the base moves.
  • If the ref is missing, the repository reports an error, or git does not answer in time, that check is skipped and the reason shows in the last result on the rule card (Ref not found, Repository error, git timed out). These do not count as consecutive failures, so the rule is not turned off automatically.
  • If the previous run is still in the queue (even when the If the previous run is still in the queue condition is Skip this run), no new run is created and the base stays put. Once the previous run ends, the next check creates one run from the base to the latest commit.
  • If the Skip a run when weekly usage is over the limit condition applies, one skipped run is recorded in the run history and the base moves. That range is not processed again.
  • Each run in the run history shows the range it covered, like Range 1a2b3c4..5d6e7f8.
  • ▶ Run now runs from the base to the current ref and does not move the base, so automatic detection is unaffected. If there is no base yet, the current commit is the starting point.

Only local refs are compared

  • CmdQ does not run git fetch and compares only the refs on this Mac. To follow the remote repository, enter something like origin/develop in git ref; changes are detected when you fetch yourself.
  • CmdQ installs no hooks or files in your repository. On each check it reads the commit the ref points to and compares it with the base.

Only when there is a PR merge commit

When on, a run is created only if the new range contains a merge commit (a commit with two parents) or a commit title with (#number) or Merge pull request. The check has limits.

  • Squash merges and rebase merges leave no merge commit. Unless the title has one of the patterns above, they are not detected.
  • CmdQ does not ask GitHub for PR information; it looks only at the commit history.

Write to materials folder only

When you turn on Write to materials folder only in the rule editor, items this rule creates can write only to the project's materials folder. It works with every repeat type and applies to every step of a chain. A rule with it on gets a Materials folder only badge on its card.

  • Allowed: reading repository files (Read, Grep, Glob), read-only git commands (diff, log, show, rev-parse, cat-file, merge-base, ls-tree), and writing files inside the materials folder.
  • Denied: editing repository files, git write commands such as commit, push, and checkout, options that make a read-only git command write a file such as git diff --output, and your own MCP and plugin tools.
  • These runs do not use your permission settings. They run in dontAsk mode, so only what is explicitly allowed gets through, and a denied attempt fails without a prompt.
  • If materials change, the run waits for your Keep or Revert confirmation even without a [자료] marker.
  • The restriction does not apply when you open the item in an interactive terminal. An item opened in an interactive terminal runs with your own permission settings. The restriction covers only items the queue runs directly.
  • The restriction is saved on the items when a run is created. If you later turn the option off or delete the rule, run items already created stay restricted, including retries and continued sessions. Turning the option on also applies it to items created before.
  • These runs start with --safe-mode, so project and user CLAUDE.md files, skills, and hooks are not loaded. Put the instructions you need in the command itself.
  • In these runs the [자료] block carries edit rules instead of the "materials are read-only" rules. Memos and copied files that are not references may be fixed with the smallest change to sentences, numbers, or base commits that no longer match. Saved link copies and references only get proposals in _proposals/.
  • If write access to the materials folder can't be set up (a material path has a character that can't go into a permission rule, or reference materials can't be read), the run goes ahead without write access and the run history notes Ran without write access to the materials folder (check material paths and reference materials).
  • Limit: when a read-only git command was given a path outside the repository and the materials folder (including the target of a symlink inside the repository), claude refused it (measured with claude 2.1.323). This protection is claude's own path check, not a rule CmdQ adds, so it may change with claude. External diff and textconv commands set in the repository config are blocked only when turned on by a flag.

Conditions

  • Skip a run when weekly usage is over the limit. The Threshold (%) is 1 to 100, and the default is off. If usage is unknown, the run is not skipped. It runs, and the run history notes Usage unknown.
  • If the previous run is still in the queue, choose Skip this run (default) or Add another. In the queue means Queued, Running, or Waiting for reset. Waiting To Do items in the To Do queue count as being in the queue too. The same check applies to rules that delete the card with Card after the run completes, so the next run still cannot overlap one that is still running. This condition also applies when a rule's times are close together: if the earlier run is still in the queue, the later time's run is skipped or added as you chose.
  • Card after the run completes: choose Follow path default (the default for a new rule), Keep the card, or Delete the card on success. What happens to a card after its run succeeds is decided in this order: the value chosen on the rule → the project path rule → keep the card. Follow path default uses the value set for this project path; if there is no path rule or it is off, it is the same as Keep the card. A rule that existed before this feature and was set to Keep the card was changed to Follow path default on update, so nothing changes until you turn on a path rule. Delete the card on success removes all cards of the chain only when the run's last step finished successfully. The run history still records it as a success, and the attachment copies are cleaned up with it. A run that failed, was stopped by you, is waiting on a limit or a decision (an unanswered question from the same session is in the decisions list), or was handed to an interactive terminal keeps its card (a deferred question counts too). So does a chain with a step started interactively, a card with a terminal attached, and a run whose session file cannot be judged. Runs executed in isolation also keep their card, and the editor shows the same note. However, if you turn on both isolation and Continue the last run's session, the continuing runs (from the second one on) execute without isolation, so their card can be deleted. The option is fixed when the run is created: an existing run follows the value it was created with even if you change the option, and turning the option on later does not delete success cards that are already there. The exception is a card you confirmed in the preview when applying a path rule: it is deleted.
  • For runs missed while the app was off, choose Run once on launch (default) or Skip. Running once creates only the most recent missed run since the last check. If several times were missed, only the most recent one runs and the rest are recorded as Skipped in the run history. Right after you create, re-enable, or edit a rule, past runs are not backfilled. Even while the app is running, runs are created once per Queue check interval, so a run counts as missed only after the longer of 2 minutes or twice that interval has passed.
  • A rule turns off automatically after 3 consecutive failed runs, and this always applies. The card gets a Turned off after failures badge and a toast says the rule was turned off after 3 consecutive failures. Only runs that end in an error count. A run you stop, a run waiting for reset, and a skipped run neither count nor break the streak, and a success resets it to 0. Turning the rule back on clears the badge and the count. Unless Notification style is set to Off in Settings, you also get a system notification. This one doesn't depend on the card's 🔔.
  • A run handed to an interactive terminal, or started interactively from its card and finished, is recorded as Succeeded and resets the failure count to 0.

Project path rule

Instead of choosing per rule, you can set the Card after the run completes value once for a project path, in Settings › Per path › Schedule card cleanup.

Completion criteria and exceptions

Both fields in the editor are optional. What you write is appended to the end of the command under a fixed heading. In a chain, it goes on the last step.

  • Completion criteria (optional): state how to judge whether the result is useful. It is appended under the heading [완료 기준].

  • CmdQ does not judge whether a result met the criteria. You check it yourself with View the response on the run item.

Isolated runs

When two tasks edit files in the same path at the same time, one set of changes can overwrite the other. An isolated run puts such an item in its own git worktree next to the repository, and when it ends you decide what happens to the result. Nothing is merged automatically. Items that are not isolated run exactly as before.

Turning it on

  • Turn on the Isolated run switch on the third row of the add bar before you add the item. It is off by default. The switch appears when the target is Path. For session or interactive targets, the switch doesn't appear. With a folder that isn't a git repository, a missing git, a git older than 2.5, or a bare repository, the switch stays off and the reason appears on the line below. For a folder that isn't a git repository it reads "Isolated runs and other git features are unavailable because this is not a git repository".
  • When the same path already has a running or queued task, a Run isolated? button appears next to the switch. Clicking it turns the switch on. It is only a suggestion, so you can ignore it and add the item as is.
  • Turn on Always isolate for a path in the Isolated runs section of Settings. The switch then starts on when you pick that path. If you turn it off before adding, that item does not run isolated. Items that reach that path without the add bar, such as recurring schedule runs, run isolated.
  • A Queued card that hasn't started has an Isolate or Don't isolate button. Running and finished cards can't be changed.
  • Turn on Run isolated in a recurring schedule rule and the items that rule creates run isolated.
  • Cards for isolated items carry an Isolated badge.
  • In a path that isn't a git repository (including a workspace created from a proposal and registered without git), isolated runs can't be used. The switch doesn't disappear in such a workspace: the same notice shows on the line below the disabled switch.
An isolated run separates only the card's target repository. If the task changes another repository (such as another module of a multi-module workspace), make that repository the card's target. Changes made directly in another repository are not part of the isolation result, and merge and discard don't reach them. The same note appears below the third row when you turn the switch on.

Worktree folder and branch

  • The worktree is created beside the repository folder as ../{repository folder}-cmdq-{item number}. For example, item 12 in ~/work/app runs in ~/work/app-cmdq-12.
  • The branch is named cmdq/item-{item number} and starts from the current HEAD of the original repository.
  • When the run ends, CmdQ commits whatever is left in the worktree as [cmdq] item #number. The Files to copy and the paths in Leave out of auto-commit below are left out of that commit.

Each file shows its current state (modified, new, ignored by git, and so on); click it to see its diff (tracked files) or content (new files and files outside any repository). Even when the result is No changes, an Outside changes button opens the list if such files exist. Merge and discard don't apply to these files, so handle them in that repository yourself. The decision sentence in the diff window's bottom bar also notes that they stay as they are.
  • The list finds paths changed with file-editing tools in the run log. For each repository found that way, its other uncommitted changes (except files ignored by git, up to 200 per repository) are listed too under Not in the run log. They may have been changed by shell commands or already been changed before the run, so check the content. N outside on the result strip counts only files found in the run log. For a repository where the run changed files inside .git/ or a .gitattributes file, git is not run and only file contents are shown. Files changed by shell commands outside a git repository may be missing. Claude's scratch folders (/tmp/claude-*) and ~/.claude are not included.

Check at startup

An isolated worktree can be left behind if CmdQ quit before you handled it. At startup CmdQ looks for these worktrees and removes only the handled ones without changes. Ones that still have changes, haven't been handled, or have no record in this app stay. Handle the unhandled ones from their cards; only handled ones that still have changes, ones with no record in this app, and ones whose card has no worktree record are counted in a "Leftover isolated worktrees" notification. You can open those folders next to the repository and clean them up yourself.

Reverting a regular item

Items that are not isolated can also go back to how things were before they ran. Turn on Save a checkpoint before each run under Queue execution in Settings (off by default), and CmdQ records a git checkpoint (HEAD plus uncommitted changes) right before each path item runs. Revert to before this run on a finished card asks for confirmation, then restores the path to that checkpoint.

  • Before reverting, the current state is backed up with git stash. The backup name appears in the completion message, and you can find it in git stash list to recover it.
  • Changes made by other tasks in the same path can be reverted too.
  • If untracked files are too many or too large for the checkpoint limit, the item runs without a checkpoint and a notification appears. That item can't be reverted.
  • Reverting is refused while an item in the same repository is running, waiting in the auto queue, waiting for a limit reset, or has an interactive terminal open. While a revert is in progress, new terminals can't be opened for regular (non-isolated) cards that use that repository. Isolated cards and reattaching to a terminal that's already open are not affected.
  • Untracked files that existed before the run are part of the checkpoint and come back with their pre-run contents. Files ignored by .gitignore are left alone.
  • If you switched branches or rewrote history (reset, rebase, etc.) after the checkpoint was saved, nothing is reverted. The confirmation shows how many commits came after the checkpoint, and after reverting they stay under refs/cmdq/revert-backup/… so you can recover them with git.
  • The backup ref holding the pre-revert HEAD is kept even when there was nothing to back up, and its name appears in the completion message. It is never deleted automatically; remove it with git update-ref -d <ref> when you no longer need it.
  • Isolated items don't have this button. Choose Discard to undo their result.

Attachments

Attach the files, links and memos a task needs. Attachments belong to a session, and every command in that session shares them.

Adding

  • In the add bar: File, Link or Memo. They're saved with the new command when you add it.
  • On a card: open 📎 and add from the drawer.
  • Drag files from Finder onto the add bar or an open drawer.
  • Links must start with https:// or http://. Memos are Markdown.
  • 📎 on a bookmark card or a terminal works on the same session, even after the card is deleted.

Project materials

Keep documents, folders, memos and links for each project tab (path), and let claude answer or work from them. Attachments belong to a session; materials belong to the tab path, so every command and terminal on that path shares them.

This feature is a Pro candidate and carries the Pro Preview badge. Until the official 1.0.0 release, it's free for everyone.

Collecting materials

  • The materials bar for the active tab sits at the right end of the scope bar above the queues. It shows the tab name, the number of materials and, when something awaits review, an N awaiting review pill. Project tabs show only the name and ×.
  • Click Materials (⇧⌘M) in the materials bar to open the materials drawer for that path on the Materials tab; press the same shortcut again to close it. The drawer sits on the right without covering the queues; the Pro Preview badge sits next to the close button. The drawer remembers two widths separately: list screens (460px by default) and wide screens such as a material's detail, the collect preview and the Links tab (920px by default, 560–1100px with the handle); double-click the handle to return to that screen's default width. Switch with the Chat, Materials N and Links N tabs at the top. The numbers are the number of materials and linked modules, and when link suggestions are waiting they show together, like Links N · N suggested.
  • Add materials with the toolbar above the list: File, Folder, Link, Memo and MCP are always visible. Choosing Memo or Folder marks that button as the selected tab and the add form takes the list's place until you finish or cancel. While there are no materials yet, the empty list explains this.
  • The list is grouped into memos, files, folders and links. Click a group header to collapse it. Click an item to open that material's detail screen in place of the list, and go back with ← List. The detail screen gives most of its space to the viewer, and editing the summary and keywords is under the collapsed Summary · keywords · source. An action row under the detail title always shows Ask about this, Save again, Edit link (links only) and, at the far end, Delete. List rows also always show a dimmed rename ✎ and delete ×. The row × and Delete on the detail screen don't delete right away: a confirmation first shows the material's kind, for a link the number of sub-pages deleted with it, and that this can't be undone. The × on card and session attachments still deletes at once. To delete several at once, use Select at the top of the list. Materials changed without approval show Awaiting review, and materials without a summary show No summary, each as a dot with grey text. Kinds are told apart by icon shape, not color.
  • Click Select at the top of the list to show a checkbox on every row; clicking a row then toggles its selection instead of opening the detail screen. Select all picks only the rows you can see and skips rows in collapsed groups. Rows you already selected inside a collapsed group stay selected and are counted and deleted too. The count shows as N selected, and Clear selection empties it. Delete selected opens a confirmation that shows how many materials will be deleted, the count for each kind, and how many sub-pages saved with links go too; nothing is deleted until you click Delete. Delete selected is disabled while nothing is selected, and it deletes up to 100 materials at a time. If some can't be deleted, the deleted ones leave the list, the rest stay selected, and their names and reasons appear inside the drawer. Turn selection mode off with Done or Esc to clear the selection; clicking a row opens the detail screen again. In selection mode, Space selects or deselects a row, and Delete or Backspace opens the delete confirmation. Esc first turns selection mode off. Space, Delete and Backspace do nothing while the cursor is in an input field.
  • A file material's viewer depends on its extension. Markdown (.md and similar) switches between Markdown and Raw text; HTML between Rendered and Raw text; CSV and TSV between Table and Raw text. The HTML preview runs no scripts and loads no external images, CSS or fonts (only inline styles and data: images in the document show). If the document tries to navigate to another page, CmdQ blocks it and restores the original; a document that tries on every open has its preview closed and you're asked to view the source. A table draws only the first 1,000 rows and 200 columns; see Raw text for everything. JSON, XML, YAML, source code, .txt and .log show as raw monospaced text only and are not interpreted as Markdown (JSON isn't folded or re-indented). A file with no extension, or an unknown one, is judged by its MIME type. Text opens up to 2 MB; above that, use Show file location and open it in another app. Images and PDFs preview in place. The attachment viewer works the same way.
  • The ✎ next to the title at the top of the detail screen renames the material. Enter or moving focus away saves and Esc cancels; an empty name isn't saved (Enter shows “The name can't be empty”; moving focus away cancels quietly). It works like the ✎ on a list row. For a link material, Edit link in the detail screen's action row, or inside Summary · keywords · source, changes the Address and Title together. Only http:// or https:// addresses are accepted. Saved pages stay as they are, and the next Save again fetches from the new address.
  • Two tabs share materials only when their paths match exactly. A trailing / is ignored. A tab on a subfolder, or another worktree of the same repository, has its own materials.
  • Closing a tab keeps its materials, and they come back when you open a tab on the same path. You delete materials only from the materials view.
  • A project can have up to 100 materials. A folder counts as 1, however many files it holds.
  • Project memos are also saved as files under memos/ in the materials folder, so claude can read them. The memo in the materials view is the source; when you edit a memo, CmdQ updates its file to match.

Folder materials

  • Under Folder in the add toolbar, type exclude patterns (optional) and pick a folder with Choose folder. CmdQ copies the folder, so the original is never touched.
  • Symbolic links are skipped, not followed. .git, node_modules, target, dist, build, .DS_Store, .venv and __pycache__ are always left out, at any depth.
  • Exclude patterns use gitignore syntax, for example *.log or build/.
  • A copy can be up to 500 MB after exclusions. A larger folder is stopped before copying starts, and CmdQ asks you to add exclude patterns or add the folder in parts.
  • When the original changes, open the folder material and click Re-import. CmdQ then reports how many files changed, were added and were removed.
  • CmdQ remembers the exclude patterns you typed when adding the folder and applies them again on re-import. If you typed none, only the default exclusions apply.
  • If adding a folder skipped symbolic links or files it couldn't read, CmdQ tells you how many, for example "Folder added. Skipped N link(s) and N unreadable file(s)."
  • File materials also remember where the original is. Open a file material and click Re-import at the top; if the original is unchanged, the copy is left as is. Files added before CmdQ started remembering the original show the button turned off, so add them again.
  • When you open the materials drawer or materials change, CmdQ compares the original of each file and folder material with its copy once. If the original differs, a Source changed pill appears on the row and the detail screen; if the original can't be found, Source missing. CmdQ doesn't keep watching originals and never re-imports on its own.

Links and linked subpages

  • Adding a link runs on its own screen that starts from Link in the add toolbar, in the order Address → Collect → Choose. Collecting sub-links and the Choose pages to save step below both happen there, and you return to the list when it ends.
  • On a link material's detail screen, Esc goes back to the list even when your input is inside the web page; press Esc again to close the drawer.
  • Like attachments, link materials open in the in-app web view with your sign-in, and page text is saved only when you ask (Attachments). Text saved with Save text in the link's web view also goes into the materials folder, where claude reads it.
  • Turn on Also save linked subpages when adding a link, and CmdQ follows links on the same origin (same scheme, host and port), nearest first, until no new links turn up or the depth limit is reached. Webview collection takes a Depth (0–10) (the default 0 saves only this page; 1 also collects the same-site links on it), and pages load one at a time.
  • Collecting needs the link's web view, so when you start, CmdQ opens the link in the web view first and then begins.
  • When you start collecting and Claude Code has an MCP server that can take that address (for now, a GitHub server for GitHub issue, PR, and file addresses, and a Dooray server for Dooray task addresses that include the project ID), the collect panel shows “Auto: collect with MCP · server name, and hand pages it cannot fetch over to the webview” and a Collect with the webview only checkbox. The box is off by default; turning it on starts with the web view. The app knows servers only from the names and status that claude mcp list reports, and it neither reads nor stores MCP tokens, credentials, or config files. Claude Code and the MCP server handle authentication. If the matching server needs authentication, it says “MCP · server name needs authentication” and collects with the web view only. With no matching server, or if the list can't be read (including any address outside GitHub and Dooray), the method choice is skipped: only the depth input and Start collecting and Cancel show, and it collects with the web view. If an MCP start on a Dooray address is rejected, collection continues with the web view and shows “The Dooray MCP lookup failed, so this is collected with the webview instead (cause: …)”. Collecting starts only when you click Start collecting, and Cancel closes the screen.
  • When Collect with the webview only is off (MCP), enter a Depth (1–10). The default is 3. CmdQ follows links in page text only that deep from the starting address, and if links were skipped because of the depth, it says “N links were not followed because of the depth limit”. Webview collection's depth is Depth (0–10), set as above. The 500MB size limit and the 5,000 address limit are the same for both methods.
  • For every page, MCP collection runs a collection-only claude that is allowed exactly one read tool of that server. That is why you see “MCP collection runs claude for every page, so each page costs a claude run”, and it counts toward your usage limit. A GitHub issue's text and its comment list are fetched separately, so one issue takes two runs. Turn off Also fetch comments (on by default) on the start screen to fetch the text only, in a single run. These runs load your hooks and CLAUDE.md; the app runs them in an empty folder outside any repository and uses only the tool's response, not the model's answer. GitHub issues and pull requests are saved as readable markdown with the title, state, author, labels, and body, plus a comments section after the body when comments were fetched. Files and responses in a shape CmdQ doesn't recognize are saved exactly as received. Collected text is saved in the materials folder as .md with a header that records the original address, author, update time, and how it was fetched. Pages saved earlier as raw JSON count as changed on the next re-save even if their content is the same, and comparing them with the original reports a different save format. Ask materials and summary runs block your MCP servers by default, and summary runs always do. The only exception is a chat where you turn on Also ask MCP (Ask materials (chat)).
  • In MCP collection, links inside the same repository are followed by default. GitHub links to other repositories appear only as “Out of scope” candidates, and only the ones you check in the other-site link list below are fetched. Links MCP could not open are gathered under “Links MCP could not open (only the ones you choose are fetched with the webview)”, and you can pass the ones you choose to webview collection with Fetch with webview.
  • When webview collection lands on a sign-in page, it pauses and says “Collection paused because a sign-in is required. Sign in on the open page, then resume.” The address appears next to Sign-in page:. If the page redirects to a sign-in server on another host (SSO), collection opens the page once more so the web view shows that server's sign-in screen, then pauses; that server's address appears next to Sign-in page:. Sign in yourself in the open web view, then click I signed in, resume; collecting continues from the page that was redirected, with the same limits and visit history. The app never reads or stores passwords or cookies. A page that MCP collection could not reach because of authentication is only marked Sign-in required in the tree.

  • Only one subpage collection runs at a time across the app. If you start one, or add an other-site link to a finished collection to run it again, while another is running, you're told to start again after it finishes or you stop it.
  • While collecting, you see pages saved and queued and the time elapsed. Stop ends it. Links whose address path or query contains words such as logout, signout, delete, remove, approve, reject, unsubscribe, cancel, reset, archive, publish, checkout or purchase can change state, so they aren't followed. Words such as accept, verify, subscribe, vote, submit, pay, order and enable are checked in the path only, so sort and setting values in the query (such as ?order=desc) aren't judged. When in doubt CmdQ leaves a link out, so ordinary addresses such as /blog/archive or /Headers/Accept can be skipped too.

A collection that starts from an internal address has no such limit. CmdQ also resolves names and skips links that lead to a private address, as well as dotless names and internal suffixes such as .internal. If a name can't be resolved the link may be skipped for a moment, so collect again shortly after. It can't catch a name that changes to another address at connection time. If a page moves to a host CmdQ hasn't seen while collecting, that page can stay in the tree as Not received. If the start address redirects to another address, enter the address it lands on as the start address.

Click an address (or its title) to open a preview under the row, and click again to fold it. A page received through the webview shows a screenshot thumbnail; when there is no thumbnail (a page received through MCP, or a capture that failed) or it can't be drawn, the first 600 characters of the page text show instead. Clicking this way doesn't change the checkbox; only the checkbox in front of the row does. A row that wasn't received can't be checked and carries a reason such as Not received (timed out), Not received (navigation blocked), Not received (no page text) or Sign-in required.   • Links to other sites are listed separately, and only the ones you pick are collected with Collect. Each picked link is followed to the end within its own origin, by the same rules.
  • If Collect on an other-site link doesn't start collecting (the collection was stopped or ended by an error or limit, or the link was already added), the view doesn't switch to collecting and you see "Collection did not start from this link."
  • The copy of one link material can be up to 500 MB. At that size, collecting stops and shows the pages received so far.

Adding and managing MCP servers

When a project tab is open, the right side of the scope bar shows one MCP chip. It shows how many of this project's servers are on out of the total (for example MCP 2/3), or only MCP when there are none. A green dot appears only when at least one server has been confirmed connected with Check connection. Click the chip to open the MCP connections window right away, with no menu in between. The window has two panes. The left pane is the server list: under the This project and Registered in Claude Code groups, each server shows a status dot, its name, a status word (Not checked, Connected with its tool count, Needs authentication, Not connected, Off) and an on/off switch. Only Not connected is shown in red. Opening the window does not run any server, so a server you have not checked yet shows Not checked. Below the list, Find in hubs… and Use a Claude Code server… are always visible. The right pane shows the details of the server picked on the left (the first one at first). The two buttons switch only the right pane to hub search or to picking a registered server, and the server list stays in place. With no servers, the list says “No MCP servers have been added to this project.” When the window is 900px wide or narrower, the left list folds into a horizontal strip at the top. Claude Code servers added to this project also count in the chip (Servers the chatbot uses and MCP collection). Everyone can use the server list, tool selection, Claude Code server cards, and collection settings. Only hub search and adding from a hub carry the Pro Preview badge, and they are free until the official 1.0.0 release.

The MCP connections window closes with Esc even after a click on an empty spot moves focus out of the window, and focus returns to the MCP chip. The only window that opens on top of it is the add confirmation. While that is open, one Esc closes only the confirmation, and focus returns to the Add… button you pressed.

  • Find in hubs… at the bottom left of the MCP connections window turns the right pane into hub search, and the bottom row says “Pressing [Add…] shows the command that will run first. Saving happens only in the confirmation dialog.” Picking a server on the left goes back to its details, and until you close the window your search terms and results are still there when you come back. Opening the search pane sends nothing. When you enter search terms and press Search, CmdQ queries the Official MCP Registry and the Docker MCP Catalog together. The Registry receives only the search terms; for the Docker MCP Catalog, CmdQ downloads the public catalog file and filters it inside the app. Each hub shows up to 30 results. If one hub fails, the other hub's results still appear and the failed hub shows the reason. Results are kept in memory only until the app quits. Smithery is not included because its search does not work without a key.
  • Each result card shows the Publisher, Authentication, and Required environment variables, with an Add… button for each run method (stdio package, Remote URL, Docker image).
  • Add… opens a two-step confirmation window. Step 1, Review what runs, shows the third-party code warning, the note that raw MCP responses may remain in the Claude session history (~/.claude/projects), the server name, a command block, the pinned version, tag, or digest, the hub source, and the names of the requested environment variables (Required or Optional). The command block shows the command and arguments that will be saved without changing a single character; for readability it only starts a new line before options that begin with -. A Docker image reference is underlined, and a remote server shows its URL and the host it connects to instead of a command. Next goes to step 2, Location & values, where you choose where to save it and enter environment variable values. Back returns to step 1, and nothing is saved until you press Confirm and add. After 10 minutes the window says the confirmation expired and goes back to step 1 so you confirm again. If a Required value is empty, it does not try to save and moves focus to that box. If saving is rejected and what will run changes while it is prepared again (a Docker server gets a new label value each time), the window goes back to step 1 with a note that it changed, so nothing you have not seen is saved.
  • Only servers with a pinned version can be added. Packages must run through npx or uvx with an exact version (semver for npm, PEP 440 for PyPI); ranges and tags are not accepted. An npx package name must be name or @scope/name. Docker images need a tag other than latest or a digest, and an image name that already carries a tag cannot get a second one. Remote servers must be Streamable HTTP at an https address, and for a remote server that needs auth headers (Authorization, an API key header, and so on), step 2 of the confirmation window takes the header values and stores them only in the Keychain; the settings hold only references such as Bearer ${CMDQ_MCP_…}. Step 1 shows the header names and the stored form, without values. For a header that uses an optional value, step 2 shows “Leave it empty and this header is not sent” on that value’s row, and leaving it empty saves the server without that header. CmdQ does not add a remote address or a package or image name that contains $, so that Claude Code never replaces a ${…} in an address with a secret value. Check connection sends the headers filled from the Keychain; material chat, collection, queue runs, and .mcp.json let Claude Code replace the references when it runs, and the values reach only that run's environment variables. Environment variables a server's package needs stay with that package row and are not mixed into its remote row. CmdQ does not add a remote server whose address is an internal or special IP (private, loopback, link-local, CGNAT, 0.0.0.0/8, multicast, broadcast, reserved (240.0.0.0/4), IETF protocol assignments (192.0.0.0/24), benchmarking (198.18.0.0/15), documentation (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32), 6to4 relay (192.88.99.0/24), Teredo (2001::/32), discard (100::/64), deprecated site-local (fec0::/10), or local-use NAT64 (64:ff9b:1::/48), including an IPv4 address carried inside an IPv6 address), or a server that asks for an environment variable that can change how programs run, such as NODE_OPTIONS, PATH, DYLD_*, LD_*, npm_config_*, PYTHON*, DOCKER_*, TMPDIR, JDK_JAVA_OPTIONS, RUBYLIB, GCONV_PATH, HOSTALIASES, or proxy (HTTP_PROXY and others) and certificate (SSL_CERT_FILE, CURL_CA_BUNDLE, OPENSSL_CONF, and others) variables. CmdQ checks saved servers against the same rule again right before a connection check, material chat, collection, or queue run; if one matches, it does not read the Keychain values and stops that run (names added to the rule later are blocked too). CmdQ does not add a server whose name already exists in the project .mcp.json, the app storage, or the servers registered in Claude Code.
  • Save to offers two places. The default, CmdQ app storage, leaves project files alone and keeps only the server definition in the app database. With Project .mcp.json, CmdQ adds this one server entry to the file's mcpServers and leaves the other entries and their order as they are. claude sessions opened in that folder use the same server. If the file cannot be read, CmdQ does not change it, and when you remove the server it takes out only an entry that still looks the way CmdQ wrote it.
  • Enter environment variable values in Environment variable values (saved to the Keychain) in the confirmation window. Whichever place you choose, the values are stored only in the macOS Keychain; the app storage and .mcp.json get only reference names such as ${CMDQ_MCP_…}. If you leave a variable marked Optional empty, CmdQ neither saves it nor writes a reference for it, so the server runs without that variable (a Docker server keeps the -e name in its run arguments exactly as the confirmation showed it, but CmdQ passes no value for it). Because .mcp.json may be committed to your repository, the confirmation window says so. CmdQ reads the values from the Keychain only for a run and passes them only as environment variables of that run. Check connection, material chat, Collect from an MCP server, and queue runs do this for servers in both places; queue runs do it only for servers that are on and have Use in queue runs turned on. CmdQ does not pass the values to a claude session you start yourself in the same folder.
  • Picking a server on the left shows its details on the right. The header has the status dot and name, then one line with the kind, where it is saved (App storage or Project .mcp.json) and the state (Not checked, Connected, Needs authentication, Not connected, Off), with Check connection and Remove always visible on the right. Below that, a card holds the Use in auto queue (all tools) switch and its note. Turn a server on or off with the switch on its row in the left list; you do not have to pick it first. Opening the window does not run any server. Only Check connection starts the server (or connects to a remote one) to fetch its tool list. If the remote server's address (domain) cannot be resolved, CmdQ says so separately from a start failure: “Couldn't resolve the server address (domain).” Right after you add a server from a hub, the right pane switches to that server's details and checks only that server. Remove needs a second press on Confirm remove, and it also deletes the Keychain values and that server's chatbot assignment. A Docker image server is saved with --label cmdq.mcp.server=server-name and --label cmdq.mcp.id=16-hex-digits (a random value made when you add it) in its run arguments (the add confirmation shows them too), and removing it deletes only the containers that carry both labels from the saved arguments, using docker rm -f. A server with the same name in another project keeps its containers. If Docker is missing or the containers cannot be deleted, the server is still removed. The labels hold nothing derived from the project path, so a .mcp.json that may be committed carries no path information. Servers without both labels (including those added before the labels existed) are not covered. You can also remove a server whose entry you already deleted from .mcp.json yourself; CmdQ does not put the entry back.
  • When checking a connection, CmdQ does not hand its own environment variables to a local server. It passes only PATH, HOME, USER, LANG, LC_ALL, TMPDIR, and SHELL (those that are set) plus that server's Keychain values. For a remote server, CmdQ resolves the address first; if any resulting address is one of the internal or special IPs listed above, it does not connect and shows Not connected. Otherwise it connects directly, without the system proxy (HTTPS_PROXY and others), only to the addresses it resolved, so the check can fail on a network that only reaches outside through a proxy. A Docker image server is started for each check with its own container name of the form cmdq-mcp-server-name-… and a temporary cidfile, and the container is deleted with docker rm -f when the check ends, whether it succeeded, failed, or timed out. If a check or a collection is cancelled or dropped partway through, CmdQ still cleans up the process group it started and this container.

On the same row it warns that the MCP servers, chatbot assignments, and Keychain secrets of those projects will be deleted, and deletes them only after you press Confirm cleanup. This cannot be undone.

Tools picked here are used by Also ask MCP in the material chat and by Collect from an MCP server (the auto queue opens all tools when the switch above is on). A picked chip is filled and has a ✓; an unpicked chip has only an outline. A chip the server declares as a write tool has a dashed outline and a Write mark. The New tool mark appears only on tools that were not in the list when you last pressed Save selection (servers saved before this change show no mark until you save once more). Tools that disappeared from the server are marked Gone. Press Save selection at the right end of the window's bottom row when you are done; it appears only while the picked server's tool chips are shown. Checks you changed but have not saved stay, even when you press other buttons for the same server or pick another server and come back, until you close the window. If you move to another server without saving a changed selection, that server’s row on the left shows “· not saved”.

With a saved choice it says “Couldn't load the tool list. Your N saved picks stay in use.”; without one it says “Couldn't load the tool list. Multi-module work

When you make a request that spans several modules in a workspace with linked modules, claude reads the linked modules' code, sorts out the change points per module, and posts the changes other modules need as proposals. You need only the link graph: no IDE settings files or personal skills.

Linked-modules context

  • When you run a queue item in a project that has linked modules, or open its card in an interactive terminal, the linked module paths are opened with --add-dir and a linked-modules block is added to the end of the prompt. For each module the block lists the path, role, relations, and the current git branch read from that module's own folder. The working path's branch is not applied to every module. If the folder isn't a git repository or the branch can't be read, the branch shows as unknown; with a detached HEAD it shows (detached HEAD).
  • The block tells claude to read the linked modules' code first to understand how they connect (APIs, shared types, callers), and to summarize the change points per module in its reply as "module → file/symbol → why".
  • Which modules are included follows the attach rules in Linked modules. Modules whose Attach switch is off and modules with Path missing are left out. In multi-module work the code is the material, so a module marked Nothing to send (no materials or root docs) is still included as long as it is on and its path exists. At most 20 modules go in, nearest first; past that, the block says how many were left out.
  • Linked module paths are treated as read-only: claude is told to change only the working path's module in this run. Queue runs start claude with --dangerously-skip-permissions, though, so CmdQ can't technically block a write.
  • The block is added on the first run of a new claude session. Runs that continue a session which already received it (resume after a limit, later chain steps) only reopen the folders, and an update block is added only when the link list has changed (see "Exploring linked modules in analysis requests" below). It is not added to Materials folder only runs. With no linked modules, no module block or module folders are added. The shared proposal instructions were updated for this feature, though, so even runs without linked modules don't send exactly the same prompt as before.
  • In an isolated run, the block names the worktree path as the folder to edit and says the original checkout is read-only for this run. Linked modules are still found from the original project path.

Other modules' work as proposals

  • Changes needed in modules outside the working path are not made by claude directly. It posts one Queue item proposal per module to Proposals. A proposal carries the target module path, a list of change points, a bundle key (group_key), this change's step id (step), and the steps that must finish first (after). The working path's own change is step origin.
  • These proposals don't count toward the 2-per-reply limit; they have their own cap of 9 cards per reply. A bundle key may use only letters, digits, ., _, : and -, up to 80 characters; a step id is up to 40; after takes up to 9 entries and change points up to 20 (300 characters each). A malformed value drops only that field and keeps the proposal. A malformed bundle key also drops the step and predecessors, leaving a plain proposal with no bundle.
  • An expanded card shows Target module, Relation to the original request (Bundle, step), Must finish first with each step's state, the number of change points, and a note. Show original request and Show bundle filter the queue view to that bundle.
  • Accepting creates a new branch and worktree in the target module and puts the item in the Auto queue. It follows the same rules as Isolated runs, so the branch is named cmdq/item-<id>. You can accept even when the target module isn't open as a tab, but only when it is a linked module of the project that made the original request (one listed in the block) or that project itself. For any other path, Accept is off if it's outside the open tabs, as for other queue item proposals; inside an open tab it goes in as a plain queue item with no isolation or bundle. Proposal content can be steered by instructions planted in repository files, so this keeps an unattended, permission-skipping run from landing in an arbitrary repository. The app checks again when it links the item and, if the check fails, removes the item it created and shows an error. A path that isn't absolute or whose folder is missing also turns Accept off.
  • Only bundle keys in the form a run hands out (item-<id>, term-<id>) make a proposal a cross-module one. The original request's card is marked as the bundle's origin step only when the proposal came from that card's session.
  • An item with predecessor steps doesn't start in the auto queue until every queue item for those steps is Done, and its card shows ⏳ (step name) waiting. If a predecessor's proposal hasn't been accepted, so no item exists yet, the item doesn't wait; the proposal card says "proposal not accepted yet — this will not wait for it". If order matters, accept the predecessor proposals first.
  • If proposals would make steps wait on each other (a cycle), the offending predecessor is dropped when the item is linked, so neither gets stuck.
  • If a predecessor's item is in To Do, the later item keeps waiting to preserve the order, and the chip and proposal card show predecessor in To Do. Move that item to the auto queue or run it; once it's done, the later item starts. If a predecessor ends with an error, the chip shows predecessor failed and its tooltip explains that re-running that item to completion or deleting it releases the wait.
  • Cards from the same request carry a 🔗 bundle chip. Click it to show only that bundle's cards, with a Showing bundle … only line above; click the chip again or press Clear bundle view to clear it. The original request's card belongs to the same bundle.

Link files and IntelliJ

CmdQ's link graph doesn't live only inside the app. It is also exported as files to each linked project folder. The app database is the single source, and the files are copies generated from it. So a hand edit is overwritten on the next export, and deleting a link in the file doesn't remove it in the app. The point is that tools can read the same module list without CmdQ.

  • The link file .cmdq/modules.json is created in a .cmdq folder directly under the project folder. It is written only at a git main repository root (where .git is a folder), not in linked worktrees or submodules where .git is a file. The first time it is created, CmdQ adds /.cmdq/ to .git/info/exclude, so it is a local-only file that never gets committed.
  • For every module reachable from this project, the file holds the name, path, distance, link source, role, and the Attach setting, plus a separate list of relations between modules. Paths are relative to this project's root (../billing) and the project itself is .. There are no absolute paths, so the file still reads correctly after a folder moves or when someone else gets it. It has no timestamps and a fixed order, so the same links give the same content, and CmdQ doesn't rewrite a file whose content is unchanged.
  • It is exported when you add or unlink a connection, change a relation or role, change an Attach switch, or open the Links tab. A change updates the files of every project connected to it, and an unlink also updates the projects that were connected before the unlink. CmdQ doesn't write to every project at app start. If an export fails, the add or unlink itself still succeeds, and the failure shows only in the status at the top of the Links tab.
  • When no links are left, CmdQ deletes the file and the empty .cmdq folder, but only if the content is still what CmdQ last wrote. A file you edited in the meantime is kept. The hash of the last written file is stored in link-file-hashes.json in the app data, so this holds across restarts.
  • If the file is corrupted, its generator isn't CmdQ, or .cmdq is a link, CmdQ doesn't overwrite it and shows left alone (file not written by CmdQ) (drift). The file is written to a temporary file and then swapped in, so a half-written file is never visible.
  • The file is read back too. Detect again reads the files of directly linked modules (distance 1) and shows links that point at this project as Link suggestions from the CmdQ link file source. Nothing is linked automatically, and a link you unlinked doesn't come back.
  • IntelliJ .idea/modules.xml adds linked modules as modules in an IntelliJ IDEA project too. It writes only when the project already has .idea/modules.xml and sits at a git main repository root, and it never creates an .idea folder. Only directly linked modules go in, including modules whose Attach switch is off. It also writes in the other repositories you are linked to, so each of them has its own linked modules; you can turn this off with the settings below.
  • For the .iml module file, if the target folder already has <folder name>.iml, CmdQ only references it. If not, it creates one under this project's .idea/modules/, and never creates files in another repository. It doesn't touch workspace.xml, vcs.xml, or misc.xml.
  • CmdQ touches only the entries it added. If IntelliJ already has a module for the same folder, CmdQ treats it as yours and leaves it alone, and on unlink it removes only entries it added. If you remove a module CmdQ added in IntelliJ, CmdQ remembers it as removed in IntelliJ and doesn't add it again. To add it back, press Add back on that module's row. The button shows only for modules in the removed in IntelliJ state.
  • For modules.xml, CmdQ only inserts or removes a single line as a text edit and never regenerates the XML, so your indentation and everything else stay as they were. If the structure isn't recognized, the file is over 1 MB, or it isn't UTF-8, CmdQ leaves it alone and shows skipped (modules.xml not recognized). If IntelliJ changes the file while CmdQ is writing, CmdQ recalculates once, and if it still differs it skips with skipped (the IDE was changing the file). Before writing, it keeps the original in the idea-backups folder of the app data, up to the latest 5 per project.
  • The Linked modules section on the Data tab of Settings has two switches: Write link file (.cmdq/modules.json) and Add to IntelliJ modules (.idea/modules.xml). Both are on by default and apply immediately. Turning one off leaves the existing files as they are, and the status shows turned off in Settings. While it is off, the files aren't updated, so a tool reading them may see stale content.
  • The top of the Links tab shows the export result on one line, such as Link file: saved · IntelliJ: modules.xml updated. The link file status is one of saved, up to date, removed (no links), none, kept (edited by hand), not written (not a git repository root), left alone (file not written by CmdQ), turned off in Settings, or could not write. The IntelliJ status is one of modules.xml updated, up to date, no .idea, skipped (modules.xml not recognized), skipped (the IDE was changing the file), not written (not a git repository root), turned off in Settings, or could not write. Module rows get a badge: IntelliJ module (added by CmdQ), already in IntelliJ, removed in IntelliJ, or not added to IntelliJ.
  • The link file isn't an IDE setting, so teammates who don't use IntelliJ and other tools can read it too. For example, a tool that gathers per-branch context (such as a branch-context skill) can read .cmdq/modules.json for the module list and merge it with the modules it reads from .idea. A reader only needs to check that version is 1.
We haven't yet confirmed in a real IntelliJ whether it reloads an externally changed modules.xml right away, whether a module pointing at an outside folder opens, or whether a Gradle re-import deletes the .iml CmdQ created. If a module doesn't show up while IntelliJ is open, reopen the project.

Exploring linked modules in analysis requests

When you run claude directly in one folder, it has a hard time following an analysis into modules outside that folder. When you ask through CmdQ, claude reads into the linked modules that fall within the impact scope and reports how each one is affected. When another module has to change, claude doesn't edit it but asks for the change through the Proposals inbox. This works from the link graph alone, with no dependence on a particular IDE or personal skill.

  • For an analysis request, you get a per-module report. Each module gets one line, "module → file:line or symbol → how it connects → impact", and the impact is one of breaking, compatible, or unknown. A module with no impact is written as checked, unaffected, and claude is told to separate what it confirmed by reading code from what it inferred.
  • Only a change request produces proposals for other modules. claude decides from the request text whether it asks for changes or for analysis. For analysis, design, review, or impact and scope questions, the changes other modules need go in the reply text as recommendations only. If it is unclear, the request counts as analysis. This keeps proposal cards from piling up in other modules when you only wanted analysis.
  • claude reads a linked module only when the request touches something that crosses a module boundary: an API call, a shared type, a schema, a configuration value, or the callers of a symbol it would change. It searches in this order: the relations and evidence in the block, the module's root docs, a search inside the module (Grep, Glob), and then only the files it needs. Reading has a budget: at most 15 files per module, and if it finds no evidence within that, it writes not found within budget.
  • Linked modules are read-only. claude is told not to change files outside the working folder, and CmdQ can't block that technically (queue runs skip permission checks). The rules text is a fixed English block inside the prompt.
  • The block is added in full on the first run of a new claude session. On a continued session, an update (<linked-modules update>) is added only when the link list has changed. Change is judged by a fingerprint built from the sorted module paths, roles, and relations, so a branch change doesn't trigger it. If the list is the same, nothing is added, which saves tokens. The update says it replaces the list received earlier. A session that started before this feature and has no recorded fingerprint receives the full block once when it is continued.
  • Each module line in the block carries the path of the module's root doc (CLAUDE.md, AGENTS.md, or README.md) as docs, plus the stored link evidence (below), up to 5 lines per module and 200 characters per line. The whole block stays within 12 KiB, and when it would go over, evidence of the farthest modules is cut first. At most 20 modules go in at once.
  • It applies to headless queue runs (normal permissions) and interactive terminals. It doesn't apply to Materials folder only runs, the 📚 Ask chat, or the 💡 idea chat. The Ask chat keeps to the materials as its evidence, so it doesn't read linked modules' source, and the idea chat has no working path yet. With no linked modules, the prompt, arguments, and environment are the same as before this feature.

Using the same list from other tools and skills

  • For every run that has modules, a JSON copy of the link list is written to run-context/<item or term>-<queue item number>/linked-modules.json in the app data, and its path is passed to the claude process in the environment variable CMDQ_LINKED_MODULES (for both headless runs and interactive terminals). A script or skill that claude calls can read the file that variable points to and get the same module list CmdQ has. A line at the end of the block also points to this variable.
  • The JSON has the link file format (version, generator, notice, role, capped, modules, relations) with information about this run added: origin (path, cwd, branch) and, for each module, abs_path and branch. The set of modules is the one in the block, and the copy is read-only.
  • If the copy can't be written, neither the environment variable nor the pointer line is added. Run folders older than 7 days are cleaned up. We haven't yet confirmed in a real environment that claude's Bash tool inherits the variable.

Link evidence

  • For modules linked through Find dependencies, the evidence (file, line, quote) is stored in the app database and goes into that module's line in the block. Up to 20 pieces are stored per pair, and unlinking deletes them. What is stored is the app's own last analysis result; quotes coming from the screen aren't trusted and stored as they are.
  • Manually linked modules have no evidence yet, so CmdQ looks for it in the background with a static analysis of the code of only those two projects. It uses half the file and time limits of Find dependencies and doesn't use claude to refine. If both repositories' current commits (HEAD) match the last scan, it doesn't scan again. That record is in memory only, so each pair is scanned once more after a restart. The scan doesn't run during a question or a run, so runs don't slow down.

Check the candidates to link and press Add links (N); they are linked and their source is recorded as Code analysis. If nothing is found, "No candidates with code evidence were found." appears.

  • Runs that Write to materials folder only don't get the guide. What those runs receive is the same as before the guide existed. A command with [첨부] does get the guide.
  • Reading only is an instruction in the guide, not something CmdQ enforces. Opening the materials folder doesn't block writes, and queued runs use --dangerously-skip-permissions, so claude can change materials if it ignores the instruction. The comparison at the end of a run also covers only runs with [자료] and Write to materials folder only runs; runs without the marker aren't compared (Materials changed without approval).
  • If the command and the guide together exceed 120 KB on the first run, the guide is dropped and the materials folder isn't opened either. No omission notice is added. Follow-up runs open the folder whatever the length.
  • There is no setting to turn the guide off. In a project with materials, existing cards without [자료] also send something different on their first run.
  • A new interactive terminal opened from the add bar can't expand [자료], so if the command contains [자료], CmdQ doesn't open it and shows "The [자료] materials marker is not expanded in an interactive session. Remove the marker or add it as a command". Use Ask materials to ask questions grounded in the materials.

Suggestions and approval

claude doesn't edit materials directly. It writes suggestion files to _proposals/ in the materials folder, and CmdQ tells it to write at most 3 per run. Each suggestion shows up in the decision inbox as a Material suggestion card, and nothing in the materials or index.md changes until you approve. Details are in Material suggestions in the decision inbox.

Materials changed without approval

Queued runs start claude with --dangerously-skip-permissions, so claude can ignore its instructions and edit files in the materials folder. CmdQ can't prevent this; it finds and reports such changes afterward.

  • CmdQ keeps a hash and a copy of the approved content of every material file. The copies sit outside the materials folder, where claude can't open them.
  • CmdQ compares the materials folder when a queued run with [자료] ends (headless, or an interactive terminal opened from that card), when an Ask materials answer finishes, and when the app starts. Terminals reclaimed by a usage limit, and terminals that end because you delete their card, are also compared right when they end. Deleting a running headless [자료] card still compares the folder when the run ends.
  • CmdQ also compares the materials folder before it changes materials itself (adding, deleting or editing materials, re-importing, saving a collection, approving a suggestion). So if you change materials while a run is going, files claude edited are put up for review instead of being overwritten by CmdQ. Re-importing a folder or saving a collection again stops without replacing the copy if that material has changes waiting for review. Handle them in the Decision inbox, then try again. Approving a suggestion also compares first, including the index.md CmdQ has not written yet, so an index that claude edited directly is put up for review.
  • If a file changed outside _proposals/ (edited, added or deleted, including direct edits to index.md), a Material changed without approval card appears in the decision inbox. Each file shows Changed by and Changes. Changed by points to the run that first found the change and is not overwritten by later checks. A queue card run shows as Item #number, and an interactive terminal without a card as Interactive terminal (first 8 characters of the session ID). A change found when the app starts shows While the app was closed (found at startup). Long stretches of unchanged lines in the diff are folded into "… N unchanged lines".
  • Comparisons and CmdQ's own changes run one at a time per project. If they overlap in the same project, the later one waits for the earlier one to finish.
  • When comparing, a file whose size and modified time match the last approved state isn't read again and counts as unchanged. So a file whose content changed while its size and modified time stayed the same isn't caught by this comparison.
  • A card for a large or binary file shows only the size instead of the changes, but the card is tied to the file's content at that moment. If the file changes again after you saw the card, Revert and Keep aren't applied and the card comes back with the current content.
  • A file that can't be read or is too large (over 256 MB) is marked Cannot check (unreadable or too large), and the other files are still compared.
  • Pick Revert or Keep for each file. Revert restores the last approved content and deletes added files. Keep accepts the current content as approved. Keeping a memo file under memos/ also changes that memo's content to the file's content. Keeping the deletion of a memo file removes that memo from the materials. CmdQ never picks for you.
  • If the memo changed in CmdQ in the meantime (a memo edit or an approved append suggestion), keeping its memo file is refused with "The memo changed in the meantime, so this can't be kept. Choose revert or check the memo."
  • Until you pick, the file stays Waiting for you and the queue keeps running. In the meantime, runs with [자료] and Ask materials also get a line saying there are changes awaiting review.
  • CmdQ doesn't overwrite a file waiting for review (including index.md and memo files) until you pick Revert or Keep. While index.md is waiting, index updates are put off, and the index is rebuilt after you pick.

Interactive terminal

A real claude session inside CmdQ, for work that needs back-and-forth.

Opening one

  • Run interactively on a card.
  • The Interactive target in the add bar (⌃3). New session, no card.
  • Session target, then ▶ Terminal. Reopens that session.
  • ▶ on a bookmark, or a row in the background terminal list.

If the session is open in another live terminal, CmdQ reattaches to it instead of starting a second claude.

Taking over a session the queue is running

Opening a session with ▶ Terminal, a bookmark or the terminal list while the auto queue is running it asks first: stop the queue run and hand the session to an interactive terminal? The question also says how many background tasks in that session will be stopped. Confirm, and the run stops, the terminal opens, and the item is marked done with a Handed off badge. Cancel changes nothing. From a card, you get no prompt. CmdQ tells you to open it again after the run finishes.

Header

  • Click the project name to copy the project path. Click the session label to copy the full session ID.
  • The first header line shows the name (command) and ✎; the second shows the project name, session and item number. Terminate, Run in background and ✕ sit together at the right end.
  • Run in background closes the window and leaves claude working. The card shows Terminal running; click it to reattach. ✕ at the right end does the same, so closing never loses work.
  • A tool row under the header always shows 📎 Attachments, ☆ Bookmark, 🔔 Input-wait alert, 🕐 Question history and Snippets with their labels. A bookmark or alert that is on shows as pressed.
  • The status bar at the bottom shows the session state as a dot and text: Connected while it runs, Session ended once the process has exited and only the window is left. On the right it lists Enter Send, ⇧Enter New line and ⇧⌘D Save diagnostics.
  • Terminate stops claude and ends the session.
  • ☆ bookmarks the session, even without a card.
  • 🕐 opens this session's question history over the terminal. Pick a question to read its reply; close it (×, Esc or a click outside) to return to the same terminal and keep typing. It reloads on every press. It stays disabled until the session id is known. Answers you sent from the decision inbox are in this list too, as questions you typed. A terminal the inbox opened to send an answer has it enabled from the start.
  • 📎 opens the session's attachments. Add, delete, reorder, edit memos or drop files, as in the drawer. Insert into terminal or Insert all pastes them into claude's input line; you press Enter yourself.
  • Snippets opens a panel to the right of the terminal. Saved commands live in two lists, Shared and This path; the two tabs in the panel header (with counts) show one list at a time. This path is unavailable in a terminal without a path. Each row shows the name and the first line of the body, with ▲▼ (reorder), ✎ (edit) and ✕ (delete) always visible. Picking a row only fills the Text to apply box below without sending anything; Apply pastes and runs it. Edits there apply to that run only. The new-snippet form stays folded until you click + New snippet. ⇧⌘P toggles the panel and opens the form. ✕ in the header closes the panel.

Background terminal list

Terminals N in the header tools (⇧⌘T) opens a list right below the button with live terminals and terminals waiting for a reset. The list header shows how many are alive and how many wait for a reset, and a click outside the list closes it. The button is hidden while there are no terminals. Each row shows a status dot and the title, with the project name, session and item number below it. Click a row to open it. Each row also has 📎, ☆, ✎ Rename and Terminate. ✎ Rename on a live terminal's row sets the name shown in the list. Press Enter to save or Esc to cancel. Once a terminal has a session, the ✎ next to the title in its window header renames it too, and a name changed there shows up right away in an open list. Saving and canceling work the same as in the list. The same name appears on the Waiting for reset row, but you can't change it there. Clear the name and confirm to go back to the original title. The name stays after you restart the app. It changes only the displayed title; the queue card's command, the bookmark alias and the path shown stay the same. While you rename a terminal, a click outside doesn't close the list; finish with Enter or Esc first. Terminate all sits on its own at the bottom right of the list and asks for a second click. A terminal opened from the list returns to the list with ⌃←. ⌃→ takes you back to that terminal. Pressing ⇧⌘T while an interactive terminal is open works like Run in background: a terminal opened from the list goes back to the list, and one opened from a card or the add bar goes back to the main window. It does nothing while another window, such as Settings, is open over the terminal.

While you work

  • When output stops for 8 seconds, you get a Waiting for input notification, but only for terminals with 🔔 on in the terminal header. A terminal opened from a queue card follows that card's 🔔. It isn't sent while you're looking at that terminal in the main window. Change or turn off the delay with Interactive input-wait alert (Notifications).
  • ⌘+click a URL to open it in your browser.
  • Mod panels take mouse clicks only with claude's fullscreen renderer: run /tui fullscreen in claude, or start it with CLAUDE_CODE_NO_FLICKER=1. With the default renderer, claude ignores the mouse.
  • Emoji count as two cells, as in claude, so tables and panels stay aligned. For a wider terminal, set Terminal window width to Full width.
  • When you come back from another app or reopen a terminal, CmdQ has claude redraw the screen. If the screen still goes blank, press ⇧⌘D to save a diagnostics file to diagnostics/ in the app data folder and attach it to a bug report. It contains terminal output, so read it before sharing.
  • If a usage limit hits, the terminal closes and resumes after the reset (Usage limits).

Decision inbox

The decision inbox gathers the questions claude stopped on across your sessions, so you can answer them in one place. When a question is waiting, a Decide N badge appears in the header. N is the number of questions waiting for you. Task proposals claude posts for your schedules and queue go to Proposals, not the decision inbox.

What it collects

  • Interview questions, where claude shows a list of choices (AskUserQuestion). These cards are marked Interview. claude opened in an interactive terminal in CmdQ gets an instruction to ask with this question tool, not in plain text, when it needs a decision from you.
  • Questions claude asked in plain text before stopping are always collected too, including questions that ask what you want, such as "What can I help you with?". These cards are marked Text and Guess and show the end of claude's last reply. CmdQ looks at the shape of the whole reply, not only its last line, so requests to choose or decide are caught even without a question mark, such as a "Decisions needed" section in the middle, a list of options, or a note on how to reply. Replies in English and Korean are both checked. Detection is still a guess, so some cards may not be real questions. Clear those with Dismiss.
  • CmdQ checks every 15 seconds and looks at every session changed in the last 24 hours. Sessions you didn't open in CmdQ show up as cards too.
  • New decision requests trigger a notification. Requests already waiting when CmdQ starts, material suggestions, and changed-material cards don't. Card 🔔 doesn't apply here; the Decision requests setting does. Sessions whose 🔔 you turned off (including with 🔕 on an alert card) don't send decision alerts (Notifications).
  • Sessions the auto queue ran are checked with broader rules. See Queue run questions below.

Queue run questions

  • The auto queue runs claude headless, so interview question prompts never appear. Queue runs therefore get an instruction, whenever they need a decision from you, to end the reply by first writing the questions and choices in Markdown and then repeating them in a decision block (JSON) in a fixed format. You can read what is being asked in the response view or an interactive terminal, and the inbox builds the card from the block. A queue run session is one the auto queue has run headless at least once. A session first opened from a queue card in an interactive terminal follows the same rules as any other session.
  • When a reply ends with a decision block, its questions and choices show up in the inbox as they are, and the card is marked Queue question. Choices claude recommends are marked Recommended, but they aren't picked for you, so choose yourself. The summary written before the block is shown on the card too, but only up to the first question line, so each question appears on the card once. A card splits up to 10 questions. With more than 10, they are listed in one numbered question that you answer by typing. Several questions or a table asked in plain text are also split up to 10, and beyond that become one question you answer by typing. Interview questions follow the question tool limit of 4.
  • If a queue run ends by asking in plain text without a block, CmdQ still guesses it is a text question and collects it, looking for several questions and recommended marks too. These cards are marked Guess, and a choice that includes (Recommended) is also marked Recommended. Conditional closings such as "let me know if you need anything else" aren't treated as questions.
  • When there are several questions, you answer them step by step, as with interviews. For text questions, only the answers are sent, one per line as A1: …, A2: …, without quoting the questions.
  • Like text questions, queue questions aren't sent to an interactive terminal. If the session is open in an interactive terminal in CmdQ, the card says "Queue questions aren't sent to an interactive terminal. Answer in that terminal".
  • Session history and the response view don't show the decision block. Only the summary, questions and choices written before it remain. If the reply is only a block, or the block is one the inbox can't read, it is shown as is. The live log you watch during a run shows the block as written.

Answering

  • Click the badge or press ⇧⌘C to open the inbox under the badge. Press the key again, press Esc, or click outside to close it. When no decisions are waiting and the badge is hidden, the key does nothing. Change the key in Shortcuts. Hover over the badge to see the current shortcut. If none is set, it says "No shortcut — you can set one in Settings".
  • When you open the inbox, the top card is expanded and the rest are collapsed. Once you answer the expanded card, the card below it expands next, or the card above if none is left below. Click a card's title row to expand or collapse it; an expanded card wraps its title so the whole title is visible. ⌘↑ and ⌘↓ move the expanded card up and down.
  • The top of an expanded card shows the Project path the question came from and the Command that led to it. Hover over a cut-off path to see all of it, and use Show all to read a long command in full.
  • Pick a choice or write in Type your own. Questions that allow several answers show checkboxes. If a choice has a Preview, expand it to read it.
  • When claude asked several questions at once, each gets a step button, and N questions left shows how many still need an answer.
  • An interview can be sent only after every question is answered. Text questions and queue questions can be sent once you answer one of them. Unanswered questions are left out, and the reply ends with a line such as 미응답(unanswered): Q2, Q3 so claude knows which ones were skipped.
  • Once the card can be sent, Will send shows the exact text that goes to claude. Check it, then click Send or press ⌘Enter. A sent card folds into a Sent ✓ line and then leaves the list.
  • For sessions that aren't open anywhere, the card shows Send to queue where Send would be. That button, or ⌘Enter, puts your answer in the auto queue without opening a terminal. Hover over it to see "Sends as a resume task · waits in the queue". A queued card folds into a Queued ✓ line and then leaves the list. To continue in an interactive terminal right away, click Send to terminal next to it. See Where the answer goes below for details.
  • Later (30 min) puts the card away for 30 minutes. If only snoozed decisions are left, the badge turns gray and reads Decide 0 · later N, and the badge and ⇧⌘C still open the inbox.
  • Dismiss removes the card without sending anything to claude.
  • The action row at the end of an expanded card always shows Send (or Send to queue and the send-to-terminal button) on the left, and Later (30 min), Dismiss and ↗ Terminal on the right. A material proposal card can be handled while still collapsed with Approve and Reject at the end of its row.
  • ↗ Terminal closes the inbox and opens that session in an interactive terminal. If the auto queue is running the session, CmdQ asks before taking it over.
  • ↩ Decisions N in the interactive terminal header opens the inbox on top of the terminal and leaves the terminal as it is. Choices and text you entered on a card stay there when you close and reopen the inbox.
  • The inbox opens on top of the attachment and schedule drawers, the interactive terminal and session history. Only Settings and About appear above it.

Text question detection

There's no setting to turn it on or off. Sessions that stopped after asking in plain text always reach the inbox, and you clear cards that aren't questions with Dismiss. Inbox (external integrations)

The inbox fetches GitHub issues and Todoist tasks and shows them as proposals for the queue. Click the Inbox badge in the header (it also shows the number of new proposals) or press ⌘L to open the list right below it, and press the key again to close it. Change the key in Shortcuts. A proposal enters the queue only after you approve it; nothing runs on its own. Proposals from a source that fetches with "Author = me" show by me in place of the author; hover to see the original author value.

This feature is a Pro candidate and carries the Pro Preview badge. Until the official 1.0.0 release, it's free for everyone.

Supported sources

  • GitHub: CmdQ runs the gh CLI on your Mac to fetch open issues from the repositories you link. It uses gh's own login; CmdQ neither reads nor stores the gh token.
  • Todoist: CmdQ fetches tasks from the Todoist API itself. It needs an API token. Write link rules the way Todoist does: @label (e.g. @cmdq) or #project (e.g. #Work). A name without @ also counts as a label. With rules, only tasks that carry one of those labels or sit in one of those projects are fetched. Project names must match exactly, including case. When there is a #project rule, the project list is read along with the tasks; if that list cannot be read (including older definitions that cannot read it), that round adds no new suggestions, does not change the path of existing ones, and leaves them as they are. Without rules, all tasks are fetched and you pick the path when you approve. If you change the rules so a task is no longer fetched, its existing suggestion stays as it is and is not marked as closed at the source.
  • GitHub MCP preset: searches issues through the GitHub MCP server you registered in Claude Code. A local (stdio) server is started for each check and closed afterwards. A remote server is connected only if it uses https and has static headers in Claude Code's settings. Remote servers without headers (OAuth sign-in) are not connected.

Turning it on

  • Click Sources in the inbox panel to open Inbox sources, then Add connection. The wizard lists its steps on the left, and each finished step keeps a one-line note of what you chose. Click a finished step to go straight back to it (going back to Sample preview fetches the sample again). In Type you pick GitHub issues, Todoist tasks, an MCP server, or your own definition. Your own definition goes Type → Tool and conditions → Sample preview → Folder links → Reply → Review and save. GitHub, Todoist and MCP servers with a prepared setup cannot be edited, so they skip Tool and conditions and take 5 steps. You can read that definition under the collapsed "Full definition" in Review and save; the "Author = me" note and the Todoist token field appear in Folder links. Without a token the sample is not fetched, and the wizard tells you which step takes the token. For sources that check each repository separately, such as the built-in GitHub source, and for sources that filter by label rules, such as Todoist, Folder links comes before Sample preview. With label rules, the sample shows only tasks that match a rule and tells you how many were skipped. The rule field shows an example for the kind of definition (owner/repo for GitHub, @label or #project for Todoist, @label only for definitions that do not read projects). If the project list cannot be read while fetching the sample, the wizard says so in one line. The bottom row shows “Step N of M · step name” on the left and Back and Next (Save and turn on on the last step) on the right. However long a step gets, that row stays at the bottom and only the step content scrolls. If you have picked something and try to close with ✕ in the header or Esc, the bottom row changes to “Stop adding this connection? Nothing you entered will be saved.” with Keep editing and Discard. Picking GitHub or Todoist again after adding it creates another one under a different name. If the connection name in Review and save clashes with an existing one, the wizard suggests another name and you cannot save until you change it. In Folder links you set link rules that tie a repository or label to a working path, and you can preview 3 sample items before saving. The sample check only reads; it never replies. A custom command also runs when the sample is fetched, so the wizard shows the command first and asks you to confirm it.
  • Every source starts off. Only sources switched On are checked on a schedule: every 10 minutes by default, and never more often than once a minute. To check right away, click Refresh or Refresh all.
  • When the current project tab's folder is a github.com repository, CmdQ reads git remote -v and suggests linking that repository to the path. The git commands used here only read, and CmdQ keeps only the owner/repo name, not the remote URL.

Proposals and approval

  • In a project tab you see only proposals linked to that tab's path; with Show all you see every proposal.
  • The list is read 100 items at a time. If there are more, Show more at the end of the list adds the next 100.
  • Old proposals are cleaned up automatically. Proposals whose original was closed, or that you ignored, are cleaned up 30 days after they last changed. Approved proposals whose reply is finished (sent or skipped), or that had nothing to reply, are cleaned up after 90 days: their content such as the title and body is erased and they leave the list. Only the source name, the link name (owner/repo for GitHub), the original item's number, the status and the processing times are kept as a trace, so the same item isn't proposed again. Proposals with a failed or pending reply, and proposals whose approved task is still queued or running, are kept. Cleanup runs only while at least one source is on.
  • Each proposal row always shows Ignore and Approve on the right. A proposal whose original was closed is marked Source closed and its Approve is dimmed and off; click Ignore to clear it from the list. A proposal with no matching path is marked No path; pick one with Choose folder when you approve.
  • Approve doesn't open a separate window. The row expands below (screen readers announce it as Approve proposal) and shows the Working path, the Command to queue and the Attached body exactly as they will be used. A long body is attached only in part. Isolated run (runs in a separate worktree) is off by default (Isolated run). Click Approve again, Cancel or press Esc to collapse it; focus returns to that row's Approve. The expanded part and your edited command stay even when the list refreshes.
  • You can edit the Command to queue before approving. Once edited, an Edited mark and a Restore original command button appear, and your edit stays even if you change the path or the isolated run. An empty command can't be approved.
  • Under Queue, pick Auto queue or To Do. The default is To Do. An item added to To Do doesn't run right away; it waits in the To Do queue until you run it or promote it to the auto queue. Either way, the result is reported back to the source by the same rules when the item finishes. The summary line at the bottom of the expanded part shows the queue you picked.
  • If the original changed after the row expanded, CmdQ asks you to review the new content first. The row's Approve only expands it; the proposal enters the queue only when you click Approve and queue.

Author filter

By default only issues and tasks you wrote are fetched, so text someone else wrote in a public repository doesn't become a command. Turning on Also fetch items written by others in the source settings shows a prompt-injection warning, and it only turns on after you tick I understand the risk. Always check the content before approving after that. With the GitHub MCP preset, lifting the filter fetches issues assigned to you instead. For a custom MCP connection, you choose the author filter in the connection wizard: pick Me only when you put author:@me in the tool query (without it, nothing is fetched), or pick All authors and confirm the same warning before moving on.

Replies

  • When a task created from a proposal ends in success, CmdQ reports back to the original issue or task. GitHub gets a comment with a result summary by default, and Todoist gets the same summary comment before the task is closed. When the reply is Complete / close and the definition has a comment action, Todoist and MCP connections likewise leave the summary comment first and then close. GitHub (gh) leaves the same summary as a comment while closing. If the source has been turned off or the Pro Preview has ended by the time of the reply, nothing is sent and the reply is skipped.
  • The success reply isn't sent the moment the task finishes. You often keep asking in the same session, so CmdQ waits until the task's session is idle: no queued or running tasks in that session and its interactive terminal not open in the window, for a set time (30 minutes by default). If you only closed the terminal window and the process is still alive, the time counts from the terminal's last input or output. A task handed off to an interactive terminal is replied to the same way once the terminal window is closed and that time has passed. If the source is off or the Pro Preview has ended, CmdQ waits and sends it once that changes. Tasks approved before this feature arrived and not yet replied to are never sent automatically; click Mark done if you want to send them. If the last task to finish in the session failed, nothing is sent automatically. CmdQ remembers when the session went idle, so restarting the app keeps counting from there. Failure comments don't wait; they're left as soon as the task fails.
  • To send it right away, click Mark done on the queue card. It appears on done cards created from the inbox whose reply hasn't been sent, and on the top card when cards in the same session are stacked into one. It doesn't appear on running, queued, waiting-for-reset, or failed cards, nor while the session still has queued or running tasks or its interactive terminal is alive (including one whose window you closed). A card handed off to an interactive terminal shows it once you end the terminal. The button disappears once the reply is sent.
  • Change the waiting time in minutes with Auto mark done on that source's row in the source settings (0–10080 minutes). Save 0 to never send it automatically, only when you click Mark done. Sources whose reply is Nothing don't have this field.
  • Failed runs are not reported by default. Turn on Comment even on failure in the wizard's Reply step to leave only a fixed failure comment, "The task failed.", on the original when the task fails; it isn't closed. The task's result content is not sent. A failure comment is left only once per original item: if you run it again and it fails again, no new comment is left, and a later success still sends the success reply. If sending the failure comment itself failed, a later success doesn't send the success reply automatically; send it with Resend reply. This needs a comment action in the definition, and the option is hidden when the reply is Nothing. For an existing source, turn it on or off with the same switch on that source's row in the source settings.
  • The summary may end up in a public repository, so it is cut to 1,000 characters, and local paths, token-like strings and environment variable values are removed before sending.
  • If a reply fails, or no result arrives for over 5 minutes, it stays under Reply failed in the inbox panel with its cause. You can send it again with Resend reply, but the reply may already have been posted and could appear twice, so check the original first.
  • A reply skipped because the source was off or the Pro Preview had ended also stays under Reply failed, marked as skipped. You can send it with Resend reply while the source is on and Pro is available; otherwise the row shows why it was refused.

Tokens and the keychain

  • Enter the Todoist token with Enter token in the source settings and Save it. The token is stored only in the macOS keychain, never in the database, settings files or logs.
  • Turning a source off doesn't delete its token; click Delete token for that. Delete on a source removes its connector file, the proposals fetched from it, and its keychain token.
  • At each check and reply, MCP sources read the server details only from ~/.claude.json: the user scope (mcpServers) and the local scope of the linked folder (projects.<path>.mcpServers). A project's .mcp.json is not read. Header tokens for remote servers are used in memory only and never stored.

Proposals

When claude thinks of something worth adding to CmdQ during a conversation, such as "this should run on a schedule" or "this should be its own queue item", it posts it here with its reasoning. When you accept, CmdQ creates the schedule or queue item the same way it would if you made it yourself. Nothing changes until you accept. Proposals is a separate panel from the Decision inbox, and it isn't counted in the inbox's totals, held items or notifications.

When there are proposals, a terracotta Proposals N badge appears next to the Decide N badge in the header. N is the number of proposals shown as cards. If no cards are shown and only folded or held proposals remain, folded N and on hold N appear as well. Click the badge or press ⇧⌘V to open Proposals, and click it again, press the key again or press Esc to close it. When no proposals exist and the badge is hidden, the key does nothing. Change the key in Shortcuts.

Where proposals come from

  • CmdQ adds an instruction describing the proposal format to headless auto-queue runs, interactive terminals opened in CmdQ, and Ask materials chats. claude leaves proposal blocks in that format in the last message of its reply.
  • For an auto-queue item, CmdQ reads the session's last reply once as soon as the run finishes and posts its proposals. For other sessions, the same scan the decision inbox uses (every session changed in the last 24 hours, every 15 seconds) posts proposal blocks when it finds them. The same proposal from the same reply is posted only once, even if both paths find it.
  • CmdQ doesn't add the format instruction to claude you start yourself outside the app, and there is no separate snippet that teaches the format. If such a session happens to leave a block in the same format, the scan above finds it.
  • The instruction tells claude not to edit cmdq.db directly and to make changes only through proposals.
  • Chats in the Ideas tab post proposals too. When an Ideas chat finishes a turn, CmdQ reads the proposal blocks in that answer and posts them, and the card gets a From an idea chat mark and a Go to chat button. An Ideas chat can't change files, so nothing changes until you accept. This chat accepts only queue item, new schedule and create-workspace proposals, and decides whether to show or fold a card by the same rules as in "Which proposals become cards" below. claude makes a queue item or schedule proposal only when it knows the absolute path of the target workspace; if it doesn't, it asks in its answer which workspace you mean. You can still send the answer yourself with Continue in queue (Ideas tab). A queue item made by accepting a card from this chat appears on the progress route (queue and result stops) in that chat's right rail (Ideas tab).
  • An Ideas chat doesn't follow instructions written inside web pages, search results, attachments or queue results, and doesn't copy proposal blocks found there. It reads them only as source material.
  • Create workspace proposals come only from an Ideas chat. A block of the same form found in the answer of an auto-queue run or by the general session scan is not posted.
  • If you delete an idea, the proposal cards that came from its chat stay. Clicking Go to chat then doesn't open a chat; the card only shows "This idea conversation has been deleted."
  • Session history and the response view hide proposal blocks. The live log you watch during a run shows them as written.

What a card shows

Like the inbox for decisions, each proposal shows as a collapsed one-line row. When you open the panel, only the top row is expanded; once you accept or reject the expanded row, the row below it expands next, or the row above if none is left below. A row has a ▸ mark and a terracotta dot, then two lines. The first line has the bold action name (Create schedule, Edit schedule, Add to queue, Continue in this session, Note only or Create workspace), an importance chip, and how long ago it arrived. If the path has a problem, ⚠ Path warning is added, and hovering it shows the warning text. The second line shows 📁 the project's last folder name only when the proposal has a path (long names are cut off; hover for the full path). Details such as the command or schedule name show when you expand the row. A collapsed row always shows a button named for what the proposal actually does (Open in editor, Add to queue now, Tell this session to proceed and so on) and Reject on the right, so you can handle it without expanding. When accepting is blocked (a path warning, a missing target rule, or a workspace whose path isn't chosen yet), the button is off and hovering it shows why. Folded and held proposals use the same row.

Click a row, or press Enter or Space, to expand it (▾); do it again to collapse it. Only one row is expanded at a time, so expanding another row collapses the previous one; the expanded row stays when the list refreshes. When you handle an expanded row, the next row in the same section (or the previous one if there is none) expands. When you expand a row, you see the bold title and one line of content at the top (for Add to queue, the first line of the command plus the step count for a chain; for Create schedule, the name and repeat; for Edit schedule, the rule number and the fields that change), then a row of chips showing importance, urgency, cost, overspec and evidence as words, and intent and expected effect up to two lines each. Click Details for the rest. At the bottom are two buttons, Accept and Reject. A collapsed row has no buttons, so you expand it and read it before deciding. A row can't be collapsed while it shows a processing error or a note that the session is held by an open terminal, and it stays open in those cases. If you expand another row meanwhile, both rows are open. All seven judgment fields are available on the card once you expand the row.

  • Intent: what it wants to do and why
  • Expected effect: what gets better
  • Overspec check: Fits or Possibly overspec, with the reason. It is possibly overspec when claude can't answer "without this, what is the user doing by hand now?"
  • Urgency: Now, Next task or Someday
  • Importance: High, Medium or Low
  • Cost: Small, Medium or Large
  • Evidence: Fact or Guess, with a quote. A proposal marked as fact without a quote is shown as a guess

Values are shown as words, not colors, and only the Possibly overspec and Guess chips use a mild warning tone. Details holds the overspec reason, the evidence quote, and what would be created, such as the name, command, repeat, completion criteria, model, effort and chain steps. An Add to queue card shows a Done when line. When you accept, CmdQ adds a blank line after the command and then a "Done when: ..." line, and that becomes the queue item. For a chain, it goes on the first (root) command only.

Create-workspace proposals

When an Ideas chat suggests starting a new project, a Create workspace card appears. It shows path candidates (a new folder or an existing repository, up to 3), a name, and the First queue items (up to 5) with their done criteria. A proposal for a new folder carries "Accepting creates a new folder at the chosen path and initializes a git repository."; one for an existing repository carries "Registers the existing folder as is. No new folder is created."

  • You can accept only after you settle on a path: pick a candidate, type an absolute path under Enter a path, or pick a folder with Choose folder…. Until then the button's tooltip says "Choose or enter a path before accepting".
  • No folder is created before you accept. When you accept, CmdQ creates the new folder, runs git init, opens the workspace tab and puts the first queue item into To Do. With more than one item, they go in as a chain that follows the first.
  • A folder that already has contents is never overwritten. "The folder already has contents, so nothing was created. Choose another path." appears and the card stays.
  • If you pick an existing repository that is already an open workspace, CmdQ doesn't open a new tab and uses the open one.
  • If a proposal for the same path is already waiting, the new one is folded as Already exists.

If you pick an existing repository whose folder isn't a git repository, CmdQ registers it as is and shows "This folder is not a git repository, so git features (such as worktree isolation) are unavailable."

If git isn't installed or git init fails, accepting doesn't stop with an error. CmdQ only creates the folder and registers the workspace, and shows "Git was not found, so the folder was not made a repository." and "Features that need git (such as worktree isolation) are unavailable in this workspace." Features that need git, such as the worktree of an isolated run, can't be used in this workspace. An old git version is reported separately: "Your git version is too old for worktree isolation. Update git to use it."

Which proposals become cards

  • The instruction tells claude to leave at most 2 proposals per reply, and only those with high importance, or medium importance with urgency now.
  • CmdQ filters again when it collects proposals, not when you open the panel, and saves whether each one is shown as a card or folded. For each reply, only the 2 proposals with the highest score (importance × urgency ÷ cost, where importance high 3, medium 2, low 1; urgency now 3, next task 2, someday 1; cost small 1, medium 2, large 3) are shown as cards. Ties go to the order in the reply. The rest are folded as Lower priority.
  • Some proposals are folded before scoring. A proposal with the same kind and target as one you rejected in the same project is folded as Rejected before. One with the same command for the same path as an existing schedule rule or a queued item is folded as Already exists. One that is possibly overspec with urgency someday is folded as Possibly overspec, someday. Rejections in other projects have no effect.
  • Click folded proposals (shown with the count) at the bottom of the panel to expand them. Folded cards show the action name, title, content, reason, path and buttons, without the judgment fields. You can still accept or reject them.
  • Notifications go only to proposals shown as cards and follow the Decision requests setting (Notifications). Clicking one opens Proposals, not the Decision inbox. In the popup and widget, proposal cards carry a Proposal chip instead of Decision needed.

Notifications

Notifications arrive the way you pick in Settings › Notifications › Notification style. System only shows macOS notification banners. Popup opens a window in the top-right corner with cards stacked in a list, and Top widget shows a band at the top center of the screen. With Popup + widget, the same alert shows in both.

  • What gets an alert: Done, failed, waiting-for-reset, and waiting-for-input alerts come only from cards and terminals with 🔔 on, and that includes system banners. Turn 🔔 on or off with the 🔔 button on a card or in an interactive terminal's header. For a terminal opened from a card, the card's 🔔 changes too. New cards start with the 🔔 default from Settings. A card's 🔔 button shows whether it is on (pressed state). Decision requests don't use 🔔; they follow Decision requests, except that sessions whose 🔔 you explicitly turned off send no decision alerts.
  • Where 🔔 carries over: the next step in a chain inherits 🔔 from the step before. Runs created by a repeat rule (including Run now) follow the rule's Alert when done 🔔, or 🔔 on new cards if the rule leaves it unset. You can still change each created card with its own 🔔. An item that resumes a session after you answer in the decision inbox inherits that session's 🔔: the session's own 🔔 if you turned it on or off, otherwise the session's last card 🔔, otherwise 🔔 on new cards. An interactive terminal without a card also follows 🔔 on new cards until you turn its 🔔 on or off.
  • Alerts that always come: reclaiming terminals at a limit, the alert that two runs changed the same file, rules turned off after failures, app updates, and isolated-run notices arrive as system banners whatever the 🔔 and per-event settings, unless the style is Off.
  • Popup and widget styles: done, input-wait, and decision alerts go only to the popup or widget, not to system banners. If the popup or widget can't be shown, a system banner is sent instead.
  • Alert titles: if you gave a terminal a name, the alert title shows that name instead of the path. Renaming applies from the next alert on, and cards already shown stay as they are.
  • Answer from the popup: a decision request with one question and a single choice shows its options as buttons plus a typed-answer box inside the card. Clicking an option sends it right away; a typed answer is sent with Send or Enter (Enter during IME composition does not send, and an empty box is not sent). Where it goes depends on the session. If nothing is using the session, it is queued at the front as a resume (the same as Send to queue in the decision inbox). If an open interactive terminal is asking with a choice dialog, the answer goes into that terminal. A text question in a session whose terminal is open is not sent from the popup; it tells you to answer in the decision inbox or that terminal. The popup never opens a new interactive terminal. If the decision inbox and the popup answer the same decision at once, only one answer is sent and the later one shows "being answered elsewhere" or "already answered elsewhere or gone". If the card closed while sending, it says the alert card was already closed. Wherever you answer, both the inbox and the popup clear that decision. Decisions with several questions, multi-select questions, or blocked decisions open with Answer in decision inbox. Answer in the widget band expands the list and moves to that card's options.
  • One-line cards: done, failed, limit-wait, and input-wait cards take one line. ↗ goes to the terminal and ✕ hides the card; hover the title to see the summary.
  • Card buttons: Go to terminal opens that item's or session's terminal in the main window. It takes the same path as running a card interactively, so it attaches to a live terminal or resumes the same session if it has ended. Decision cards have Answer in decision inbox, and proposal cards have View in Proposals. Hide clears only that card. The 🔕 (Mute) in the top-right corner of every card, decision cards included, turns off 🔔 for that session and closes all of its cards. The session's card 🔔 and terminal header 🔔 turn off together, and items that resume the session inherit the off 🔔, so no more done, input-wait, or decision alerts come from it. Turn the session's 🔔 back on to get them again. In the widget band, the 🔕 next to the latest alert does the same.
  • Widget: the band shows the pending count and the latest alert, with the card list below. Collapse leaves only the count, and clicking the count expands it again. The main button next to the latest alert handles it directly (Answer for decisions, View in Proposals for proposals, ↗ otherwise). The ✕ (Hide all) at the end of the band clears every card in both the popup and the widget.
  • Hidden cards: a hidden alert doesn't come back for the same event. CmdQ keeps this in memory only, so it resets when you restart the app. Cards for decisions answered elsewhere or cleared in the decision inbox, and cards for a session where you started new input, close on their own.
  • While you're looking: if the main window is in front and you have that terminal open, its done, input-wait, and decision alerts aren't sent. Decision alerts aren't sent at all while the main window is in front, since the Decision inbox count already shows them.
  • First launch after updating: earlier versions alerted on every finished card, but new cards now start with 🔔 off. Existing users see a one-time "Per-card completion alerts" notice on first launch. Turn on 🔔 for new cards makes every new card alert as before, and Keep as is leaves your settings alone. The notice doesn't show if Notification style is Off, or on a fresh install.

Changing a shortcut

Settings › Shortcuts lists the actions in four groups: Switch screens, Open, Path tabs and Command input. Click a key field and press the new combination. Clear sets it to None. Default restores the original.

  • A combination needs ⌘, ⌥ or ⌃.
  • A combination already in use is refused with the name of the action that has it.
  • If you had already assigned ⌘K to another action, Search starts as None. Assign it a combination in Settings to use it.
  • If you saved shortcut settings before, ⌘1 stays on Workspace and ⌘2 on Schedule, and Switch to Ideas starts as None. Assign it a combination under Shortcuts in Settings to use it.
  • You can't assign: the app menu keys (⌘C ⌘V ⌘X ⌘A ⌘Z ⇧⌘Z ⌘Q ⌘H ⌥⌘H ⌘M ⌃⌘F), the submit keys (⌘Enter ⌃Enter ⌃⌘Enter), and ⇧⌘D (save terminal diagnostics).
  • ⌘Enter inside the question search popup (continue the chosen result in a terminal) can't be changed either. It only works in the popup, so it doesn't clash with submitting from the command box. Fixed shortcuts under Shortcuts in Settings lists it together with ⇧⌘D and the other fixed keys.

When shortcuts work

  • Only while the CmdQ window has focus.
  • In a text field, only combinations with ⌘, ⌥ or ⌃ fire.
  • With a full-screen view open (terminal, history, settings), only Settings, Search, Add snippet, Back and Forward work. Decision inbox also works over an interactive terminal or session history.
  • Terminals closes the terminal list when it's open. With an interactive terminal open, it puts the terminal in the background like Run in background: a terminal opened from the list goes back to the list, and one opened elsewhere goes back to the main window.
  • Search's key goes to CmdQ, not claude, even while an interactive terminal has focus.
  • Forward only works when you press it right after Back. Pressing any other key in between (typing in the shell or the command box, Esc, another shortcut) clears the Forward history, and in an interactive terminal ⌃→ then goes to the terminal, so word movement still works. The same happens when there's nothing to reopen or the terminal has ended. Closing a window or clicking a tab with the mouse keeps the history.
  • If macOS Mission Control uses ⌃← for "Move left a space", it gets the key first. Assign Back to something else.
  • The same goes for ⌃→ and "Move right a space": if it's on, macOS gets the key first. Assign Forward to something else.

config.toml

Settings live in ~/Library/Application Support/com.doitasap.cmdq/config.toml. A few keys exist only there.

  • Quit CmdQ before editing. Saving in Settings rewrites the whole file and drops edits made while the app was running.
  • Out-of-range values are clamped to the nearest limit, and CmdQ tells you which ones.
  • A file that can't be parsed is moved to config.toml.bak, and CmdQ starts with defaults.
